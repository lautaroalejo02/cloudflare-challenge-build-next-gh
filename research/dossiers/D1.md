#### Darcs — patch theory, commutation, conflictors
- What it is: Haskell DVCS (2003+) whose repository is a *set* of patches; merge is defined by commuting patches, and conflicts are themselves a patch type.
- URLs: https://darcs.net/Theory/Conflictors · https://darcs.net/Theory/Motivation · https://darcs.net/Using/Model · https://www.cs.tufts.edu/~nr/cs257/archive/jason-dagit/tmr-darcs.pdf
- Core mechanism: Two sequential patches `A B` can be rewritten `B' A'` iff they commute; failure to commute *defines* dependency, and a "conflictor" patch encodes a conflict by storing the conflicting primitive plus the closure of what it conflicts with — conflicting sides cancel out in the repo but are recoverable.
- Transferable mechanism: Dependencies between changes are *derived* (by attempted commutation) rather than declared — a system can compute "which agent change depends on which" by testing whether patches swap cleanly, and cherry-pick minimal transitive dependency sets automatically. Also notable: Darcs has a `token replace` patch type that commutes with almost any hunk — i.e., *typed* primitive patches (rename-token vs. edit-line) that have different conflict behavior.
- Status/limitations: Purely textual granularity — Darcs docs admit it cannot detect semantic dependencies (a call added vs. a signature changed in a different region). Conflictors have known defects: commutation with conflictors is not always invertible; duplicates are a major source of bugs. Haskell codebase; nothing reusable in a Worker directly — the *idea* is what transfers.

#### Pijul & the categorical theory of patches (Mimram–Di Giusto)
- What it is: Rust VCS built on "A Categorical Theory of Patches" (arXiv 1311.3903): files are objects, patches are morphisms, merge is a pushout; when no pushout exists the file space is *extended* so conflicts become first-class states.
- URLs: https://www.lix.polytechnique.fr/Labo/Samuel.Mimram/docs/mimram_ctp.pdf · https://pijul.com/model · https://jneem.github.io/merging/ · https://refpath.github.io/nuif/research/items/patch-theory-darcs-pijul.html
- Core mechanism: The repository is a graph of byte-chunk vertices (each identified by hash of introducing change + offset) with order edges; edits are edge relabelings, independent changes commute, and conflicts (unordered alive vertices, cycles, zombies) are *stable graph states* that a later patch resolves.
- Transferable mechanism: A conflict is not an event or an exception — it is a *persistent, addressable state* that subsequent changes can heal; this inverts the merge-conflict lifecycle so "integrate everything, resolve asynchronously" is the default. A branch is exactly a set of patches, so branch state = set union.
- Status/limitations: Still 1.0.0-beta (beta.9 seen in 2025 discussion); Nest hosting service is being rewritten and there are SSH/compat complaints. Notably for this challenge: the Nest rewrite is itself TypeScript on **Cloudflare Workers + WASM** (https://pijul.org/posts/2023-05-23-nest-a-new-hope) — proof the paradigm can live on this platform. The `libpijul` core is Rust; running it in a Worker would require WASM compilation — UNVERIFIED whether it compiles cleanly.

#### Unison — content-addressed code
- What it is: Language/toolchain where every definition is identified by a SHA3-512 hash of its (name-stripped, dependency-hash-referencing) AST; code is stored in a database, not text files.
- URLs: https://www.unison-lang.org/docs/the-big-idea/ · https://www.unison-lang.org/docs/usage-topics/general-faqs/ · https://www.unison-lang.org/blog/writeup-of-our-first-unison-meetup/ · https://github.com/unisonweb/unison
- Core mechanism: Names are mutable metadata pointing into an immutable hash space; "merge" reduces to set union of definitions plus a namespace (name→hash) diff, so there is no textual merge, renames are free, and dependency conflicts/diamond problems disappear by construction.
- Transferable mechanism: If agents commit *definitions* (AST fragments hashed by content) rather than files, then concurrent adds never conflict, two agents "editing the same function" produce two coexisting hash-addressed candidates (like `frobnicate#2aQjd` / `frobnicate#9jfPv` hash-qualified names), and the merge decision is a per-name choice, not a text merge. Unison's codebase directory format was deliberately designed so git merges = union of immutable files.
- Status/limitations: Requires a language-level model (typed AST), so it only works if the system owns the language or can lift ASTs per-language (tree-sitter). Unison itself is Haskell — not usable in a Worker; the *codebase-as-merkle-DAG* model is what transfers.

#### mergiraf — syntax-aware merge driver
- What it is: Rust CLI git merge driver using tree-sitter for a growing set of languages; solves conflicts line-merge can't.
- URLs: https://mergiraf.org/ · https://mergiraf.org/architecture.html · https://mergiraf.org/usage.html · https://codeberg.org/mergiraf/mergiraf
- Core mechanism: Parse base/left/right with tree-sitter → match the three pairs of trees with GumTree → convert to PCS (parent-child-successor) triples → merge the *set* of triples → rebuild tree, check delete/modify and duplicate-signature conflicts → render.
- Transferable mechanism: Two cheap wins worth stealing: (a) run line-merge first and only do tree-merge on actual conflicts (fast path); (b) merging *sets of PCS triples* turns tree merge into set union/intersection — directly maps to a symbol- or node-granularity merge of agent changes. Declarative per-language config (teach new languages without code).
- Status/limitations: Rust+tree-sitter — compilable to WASM in principle but UNVERIFIED as a Worker package; the algorithm (GumTree + PCS) is implementable in JS on top of `web-tree-sitter`. Falls back to line-merge on parse errors.

#### GumTree — AST diff algorithm
- What it is: The reference AST-differencing algorithm (ASE'14, Falleri et al.): produces edit scripts (insert/delete/update/move) between two ASTs.
- URLs: https://courses.cs.vt.edu/cs5704/spring18/5704-GumTree.pdf · https://dl.acm.org/doi/10.1145/3597503.3639148 · https://dl.acm.org/doi/10.1109/TSE.2023.3315935
- Core mechanism: Greedy top-down matching of isomorphic subtrees (anchor mappings via subtree hash) then bottom-up "container" matching when descendants share many anchors, then an edit-script generator over unmatched nodes.
- Transferable mechanism: Hash-isomorphic subtrees = free "unchanged" detection at arbitrary granularity — a write-set detector that says "agent A moved `foo()`, agent B edited `bar()`" in one pass. The move action is what lets renames/moves merge cleanly.
- Status/limitations: Original algorithm is O(n²) worst case and doesn't scale to big ASTs; the ICSE'24 paper gives a 50–281× faster heuristic. Algorithm is simple enough to reimplement in JS (~matching on hashed subtrees) — difftastic and mergiraf are the practical references.

#### difftastic — structural diff (display-side counterpart)
- What it is: Popular Rust CLI (Wilfred Hughes) that diffs on a simplified tree-sitter syntax tree (atoms + lists), not lines.
- URLs: https://difftastic.wilfred.me.uk/ · https://difftastic.wilfred.me.uk/parsing.html · https://github.com/wilfred/difftastic
- Core mechanism: Convert tree-sitter trees to a uniform atom/list tree (delimiters folded into lists, whitespace dropped), then diff that tree so results align to syntax not lines.
- Transferable mechanism: The *lossy* simplification is the transferable idea — normalize away whitespace/formatting before diffing so "what changed" is semantic, immune to formatter churn between agents.
- Status/limitations: Explicitly does NOT do merge ("AST merging is a hard problem difftastic does not address — see mergiraf"); scales poorly with many changes, high memory; output is human-oriented, no patch generation. Rust; for Workers use `web-tree-sitter` + own differ.

#### SemanticMerge (Plastic SCM/Codice)
- What it is: Commercial "merge that understands functions" tool (2013–2022); parsed C#/Java/C/C++/PHP and merged per-declaration.
- URLs: https://www.semanticmerge.com/features · https://www.infoq.com/news/2013/04/Semantic-Merge/ · https://legacy-forum.plasticscm.com/topic/23359-end-of-the-availability-of-standalone-semantic-merge/
- Core mechanism: Merge at declaration granularity (method moves/reorders don't conflict; duplicate `using`/import clauses detected and added once) and fall back to 3-way text merge only inside a method body touched by both sides.
- Transferable mechanism: Two-level merge protocol — structural merge for placement/identity of declarations, textual merge only inside a doubly-edited body — is exactly the granularity hierarchy an agent-merge engine wants (symbol table diff first, body diff second).
- Status/limitations: Standalone product discontinued April 2022; survives inside Unity Plastic SCM. Windows/.NET only — use as design precedent, not as a library.

#### Spork, jFSTMerge, JDime — semi/fully-structured merge research line
- What it is: Java-focused research merge tools. jFSTMerge/S3M = "semistructured": AST for declarations but node bodies stay text (matched by identifier — class/field name, method signature). Spork = full AST merge via GumTree + the 3DM XML-merge algorithm, with formatting preservation.
- URLs: https://github.com/guilhermejccavalcanti/jFSTMerge · https://github.com/ASSERT-KTH/spork · https://ar5iv.labs.arxiv.org/html/2202.05329 · https://kth.diva-portal.org/smash/get/diva2:1471148/FULLTEXT01.pdf
- Core mechanism (semistructured): Superimpose declarations by *identifier* (name/signature), textually merge only within matched nodes — a cheap 80% win over line merge.
- Transferable mechanism: Identifier-keyed superimposition is the minimal viable structural merge — you don't need full AST ops, just "same symbol, merge bodies; different symbol, union." Preserving original text snippets (Spork) matters for agent output quality.
- Status/limitations: Java-only, JVM-based — not deployable in a Worker, but the semistructured design is a weekend-implementable algorithm on top of tree-sitter queries (identifier extraction is a grammar-table problem).

#### IntelliMerge & RefMerge — refactoring-aware merging
- What it is: Two OOPSLA/empirical approaches to refactor-caused conflicts. IntelliMerge (OOPSLA'19): Program Element Graphs (nodes = classes/methods/fields, edges = call/access relations) aligned across three versions via refactoring heuristics; −58.9% conflicts vs git-merge, ~539ms median. RefMerge (arXiv 2112.10370): *invert* refactorings detected by RefactoringMiner on both sides → plain text merge → replay refactorings on the merged result.
- URLs: https://dl.acm.org/do/10.1145/3361529/full/textFiles/oopsla19main-p254-p-3360596-artifact-independent-readme.txt · https://2019.splashcon.org/details/splash-2019-oopsla/53/IntelliMerge-A-Refactoring-Aware-Software-Merging-Technique · https://arxiv.org/pdf/2112.10370v2.pdf · https://github.com/ualberta-smr/RefMerge
- Core mechanism (RefMerge): Normalization-before-merge — strip a whole *class* of change (refactorings) from both sides, merge the simplified deltas, then re-apply the refactored form. (MolhadoRef's earlier version showed a 97% conflict reduction on its own repo.)
- Transferable mechanism: "Canonicalize-then-merge" generalizes beautifully to agents: if each agent's commit is *split into* mechanical transforms (renames/moves, replayable as operations) vs. semantic edits, the semantic deltas commute far more often; conflict analysis runs on the residual. IntelliMerge adds: merge on a *relation graph* (calls/accesses), not on files — conflicts become "both sides rewired edges incident to the same node."
- Status/limitations: IntelliMerge/RefMerge are Java + IntelliJ/RefactoringMiner bound — research-grade Java code. Mechanism transfers; code doesn't. RefMerge evaluation: resolves 7% of scenarios completely (vs IntelliMerge 4%) on 2,001 real merges — real but modest, so it's a conflict *reducer* not eliminator.

#### Jujutsu (jj) — conflicts as data, operation log, change IDs
- What it is: Git-compatible DVCS (originated at Google, Martin von Zweigbergk) with a different data model: conflicts are stored *in commits*, and every repo mutation is a commit in an "operation log" DAG.
- URLs: https://docs.jj-vcs.dev/latest/technical/conflicts/ · https://docs.jj-vcs.dev/latest/operation-log/ · https://docs.jj-vcs.dev/latest/technical/concurrency/ · https://docs.jj-vcs.dev/latest/conflicts/
- Core mechanism (conflicts): A conflicted commit links an odd-length list of trees — a start tree plus pairs of diffs — so a 3-way merge is literally the algebraic expression `A+(C-B)`; conflicts flatten and simplify by canceling terms, are materialized (not stored) as markers, and can be rebased/merged/backed-out while still conflicted.
- Core mechanism (op log): Every operation writes a snapshot "view" (heads, bookmarks, workspaces) as a new op-DAG node with parents — concurrent commands never lock; they fork the op DAG, and divergence surfaces afterwards as conflicted state. Two copies of a repo can even be merged via `rsync`/Dropbox.
- Transferable mechanism: Three stealable pieces: (1) **never block on conflict** — record the conflicted state as a first-class object and let resolution be a separate, later transaction; (2) the **op log gives lock-free multi-writer repo mutation** — for 100K agents, accept concurrent writes and reconcile views rather than serializing; (3) **change IDs** — a stable logical ID surviving rewrite lets an agent's "change" be tracked across amends/rebases (the PR-of-agents primitive).
- Status/limitations: Rust CLI + lib (`jj-lib`), git-backend; actively developed (~v0.3x), documented merge algebra in `merge.rs`. Compiling jj-lib to WASM for a Worker is plausible but UNVERIFIED; the conflict-expression model (`Merge::flatten/simplify`) is implementable in JS over git trees.

#### Sapling + Mononoke + EdenFS (Meta)
- What it is: Meta's source control stack: Sapling client (ex-Mercurial), Mononoke server (Rust, MySQL/S3 backends, thousands of commits/hour over tens of millions of files), EdenFS virtual filesystem.
- URLs: https://engineering.fb.com/2022/11/15/open-source/sapling-source-control-scalable/ · https://github.com/facebook/sapling/blob/main/eden/mononoke/README.md · https://github.com/facebook/sapling/blob/main/eden/mononoke/docs/5.2-mercurial-sapling-support.md · https://github.com/facebook/sapling/blob/main/eden/fs/docs/Overview.md
- Core mechanism: Centralized server holds canonical state in a simplified internal format (Bonsai changesets) and *derives* per-client views; the checkout is virtual — only files actually touched are materialized (lazy fetch on access).
- Transferable mechanism: Checkout cost should be O(what the agent touches), not O(repo): a "workspace" is a small overlay of modified files over an immutable server baseline (EdenFS's overlay/inode model). Server-side rebase on push (`sl push --to main` rebases server-side) pushes integration cost to a single authoritative point — relevant since Cloudflare Artifacts has no server-side merge, meaning *someone* must supply it; a Worker can be that server.
- Status/limitations: Mononoke/EdenFS are heavyweight Rust infra, Linux-first, not Worker-portable; Sapling's design "single-master, always-online, rebase-instead-of-merge" assumptions match a centralized agent forge well.

#### Google Piper, CitC, TAP
- What it is: Google's monorepo stack: Piper (VCS on Spanner), CitC (cloud workspaces via FUSE overlay, avg <10 local files), TAP (Test Automation Platform gating all submits), trunk-based dev with commits gated by review+tests.
- URLs: https://dl.acm.org/doi/full/10.1145/2854146 · https://en.wikipedia.org/wiki/Piper_(source_control_system) · https://abseil.io/resources/swe-book/html/ch23.html · https://static.googleusercontent.com/media/research.google.com/en/pubs/archive/45861.pdf
- Core mechanism: (a) CitC = every workspace is a named *snapshot of writes* overlaid on the repo — workspaces are data, not machines; (b) TAP = submit is gated by tests, but since per-commit testing can't scale (commit every second), TAP batches commits into "milestones" (~45 min) and does postsubmit culprit-finding.
- Transferable mechanism: When validation is the bottleneck, *bundle changes into epochs* and attribute failures afterward (culprit-finding) instead of gating each — maps to grouping agent commits into "milestones" verified together. And the overlay-workspace model makes "100K concurrent workspaces" a storage problem (~10 files each), not a compute problem.
- Status/limitations: Proprietary; use as architecture pattern only. The milestone/batching idea is directly buildable as a Durable Object + Queues design.

#### Merge queues: GitHub MQ, bors, Graphite, Uber SubmitQueue, Aviator
- What it is: Systems that serialize/parallelize landing so trunk stays green: bors (staging branch + batches + bisect on failure), GitHub merge queue (merge_group checks), Graphite (stack-aware queue), Uber SubmitQueue (speculation trees), Aviator (parallel mode + batching + optimistic validation).
- URLs: https://docs.github.com/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue · https://github.com/bors-ng/bors-ng · https://graphite.com/docs/graphite-merge-queue · https://www.uber.com/ci/en/blog/bypassing-large-diffs-in-submitqueue/ · https://arxiv.org/html/2501.03440 · https://github.com/uber/submitqueue · https://docs.aviator.co/mergequeue/concepts/batching
- Core mechanism: SubmitQueue builds a *speculation tree* over pending conflicting changes and validates multiple orderings in parallel; Uber proved landing out-of-order is safe iff all speculation-tree paths verify with the same outcome (74% wait-time improvement). Aviator adds: bisect failed batches; "optimistic validation" (wait for later batches before evicting on flaky failure); proactive dequeue when a mid-queue batch provably introduced the failure.
- Transferable mechanism: The queue is a **scheduler over a dependency/conflict graph**, not FIFO: classify changes as independent vs. conflicting (by affected-symbol/package sets, not git conflicts), run speculation trees only over the conflicting subgraph, and let independent changes land immediately. For agents, "conflict" can be computed from write-sets — cheap pre-merge analysis replaces CI as the gate.
- Status/limitations: Uber open-sourced SubmitQueue (Go, provider-pluggable). All are CI-infrastructure, not merge algorithms — they assume textual merge already works; they compose with, not replace, a merge engine.

#### Gerrit — submit requirements as data
- What it is: Google's change-based review system where "when can this submit" is expressed as declarative, versioned rules (`applicableIf`/`submittableIf`/`overridableIf`) stored in the repo's `refs/meta/config`.
- URLs: https://gerrit-review.googlesource.com/Documentation/config-submit-requirements.html · https://gerrit.googlesource.com/gerrit.git/+/refs/tags/v3.12.3/Documentation/config-submit-requirements.txt
- Core mechanism: Submittability is a *pure function* over change state (labels, files touched, comments) evaluated continuously — no human merge action; the set of unmet criteria is itself displayed.
- Transferable mechanism: Review policy as code, evaluated per change continuously, means the human decides by looking at *which predicates are unsatisfied* (a checklist), not by reading the diff — exactly the "decide without reading" review surface. Storing the rules *in* the repo (refs/meta/config) means policy is versioned and forkable.
- Status/limitations: JVM service; only the model transfers. Prolog-based custom rules exist but are legacy — the predicate model is what matters.

#### git rerere — resolution reuse
- What it is: Built-in git feature recording (conflict → resolution) pairs, auto-applying known resolutions when the same conflict recurs.
- URLs: https://git-scm.com/docs/git-rerere · https://git-scm.com/docs/rerere · https://git-scm.com/book/en/v2/Git-Tools-Rerere
- Core mechanism: Conflicts are *normalized* (marker labels stripped, ancestor removed, hunks sorted) then hashed to a conflict ID; a resolved hunks' DB answers future identical conflicts — resolution becomes a content-addressed cache.
- Transferable mechanism: Across 100K agents, the *same* conflict shape recurs massively (everyone hits the API rename). A shared normalized-conflict→resolution store means each distinct conflict is resolved once globally — conflict resolution cost scales with *distinct* conflict shapes, not agents.
- Status/limitations: rerere is local-repo state (`rr-cache`); the normalized-fingerprint idea is trivially reimplementable as a per-repo DO table keyed by conflict hash.

#### git merge-ort — merge-engine engineering lessons
- What it is: Git's default merge strategy since 2.34, rewrite of merge-recursive by Elijah Newren; detects file+dir renames, merges trees without touching the working copy.
- URLs: https://code.googlesource.com/git/+/HEAD/Documentation/merge-strategies.adoc · https://github.com/git/git/blob/master/merge-ort.c · http://public-inbox.org/git/48fc65a5-12ba-be67-2908-27a446b1f813@gmail.com/t/
- Core mechanism: Two-phase — collect merge info by recursing only into non-trivially-mergeable subtrees, then process entries; rename detection runs first and the merge *restarts* with cached renames since knowing renames unlocks more trivial subtree merges.
- Transferable mechanism: Merge operates on the **object graph, not a checkout** — a Worker can merge two repo states purely over Artifacts' trees/blobs (readTree/readBlob) with no filesystem; and "restart after global inference" (renames) is a pattern for fixpoint merges.
- Status/limitations: ort isn't exposed as a library; isomorphic-git's merge is a much simpler diff3 (see below). Relevant trick: merges of criss-cross histories merge the *ancestors recursively* to synthesize a virtual base.

#### Dolt — versioned SQL database (cell-level merge)
- What it is: SQL database with git primitives (commit/branch/merge/diff) over a prolly-tree (content-addressed B-tree) storage engine.
- URLs: https://www.dolthub.com/blog/2020-07-15-three-way-merge/ · https://www.dolthub.com/blog/2024-06-19-threeway-merge/ · https://www.dolthub.com/blog/2023-05-01-schema-conflicts/ · https://www.dolthub.com/docs/concepts/dolt/git/conflicts/
- Core mechanism: Three-way merge at *cell* granularity (rows identified by primary key; same-cell-different-value = conflict), with *schema merged separately* from data; Merkle-tree storage makes merge cost proportional to changesets, not table size.
- Transferable mechanism: Split "merge" into (a) structure/schema merge and (b) content merge with different rules — for code: merge the symbol/interface table (schema) with signature-equality rules, merge bodies (data) separately. History-independent content addressing (same data → same hash regardless of construction order) is what makes cheap dedup of agent edits possible.
- Status/limitations: Go binary + SQL server; nothing Worker-portable, but prolly-tree = implementable design (also see Noms, its predecessor).

#### lakeFS — git semantics over object stores
- What it is: Version control layer for data lakes: branches/commits/merge over S3-style objects, metadata-only branching, merge is whole-object (format-agnostic).
- URLs: https://docs.lakefs.io/latest/ · https://docs.lakefs.io/concepts/internals/ · https://docs.lakefs.io/dev/understand/how/merge/
- Core mechanism: Branch = zero-copy pointer; merge = three-way over *presence+identity* of versioned objects with coarse `source-wins`/`dest-wins` strategies; hooks (`pre-merge`) attach validation gates to the merge operation itself.
- Transferable mechanism: Cheap-branch math — 100K agents = 100K zero-cost branch pointers, cost lives only in merge; and **merge hooks** as the extensibility point (validation/quality gates run as part of merge, not as an external CI step). Also: format-specific merge strategies are a plugin slot — "merge driver per file type" maps to gitattributes-style drivers.
- Status/limitations: JVM/Go service; object-level merge is too coarse for code but the branch-is-metadata + hook model maps directly onto Cloudflare Artifacts repos + Worker subscriptions.

#### Irmin + MRDT/Quark — mergeable data types as a library contract
- What it is: Irmin: OCaml Git-like store library where the *contents type* supplies a user-defined 3-way `merge` function — Git's branch model as a generic substrate. MRDT (Kaki et al., OOPSLA'19): theoretical framework that *derives* merge functions from invertible relational specs (abstraction/concretization pairs) of a data type, implemented in the Quark tool.
- URLs: https://irmin.org/ · https://github.com/mirage/irmin · https://gazagnaire.org/pub/2015.01.OUPS.pdf · https://dl.acm.org/doi/10.1145/3360580 · https://kcsrk.info/papers/oopsla19-mrdt.pdf
- Core mechanism: A store parameterized by a `Contents` module exposing `merge: old -> a -> a -> result` — version control plumbing (LCA discovery, commit graph, branching) is type-agnostic; only the merge function is domain-specific.
- Transferable mechanism: Architect the agent forge exactly this way: repo machinery (DAG, branches, snapshots in Artifacts) is generic; each *artifact type* (AST table, test suite, spec doc, lockfile) plugs its own 3-way merge — a merge is sound iff each component merge converges. MRDT adds the deeper idea: state merge correctness can be *proved from the type's relational spec*, not hand-rolled per case.
- Status/limitations: OCaml — not Worker-deployable; Quark is a research artifact. The `Contents.merge` contract is a one-interface design pattern.

#### Automerge + Peritext — CRDTs for structured documents and rich text
- What it is: Automerge: JSON-like CRDT (maps, RGA lists, text, counters) with full-document history; Peritext (Ink & Switch, CSCW'22): CRDT for inline rich-text formatting storing spans anchored to stable character IDs.
- URLs: https://automerge.org/docs/reference/documents/ · https://www.inkandswitch.com/peritext/ · https://dl.acm.org/doi/10.1145/3555644 · https://github.com/automerge/automerge-repo-sync-server
- Core mechanism: Every inserted element gets a unique (actor, seq) ID and an origin pointer; merge = deterministic integration of all ops, convergence guaranteed without coordination. Peritext: annotations live *alongside* the sequence, anchored to opIds not offsets, so metadata survives arbitrary concurrent edits.
- Transferable mechanism: **Anchored metadata** — review comments, test status, provenance ("agent X wrote this") attached to stable element IDs inside the document, merged for free and surviving rebases; and RGA itself gives a merge model where "the merge" is deterministic integration, not a decision event.
- Status/limitations: Automerge is Rust-core compiled to WASM (`@automerge/automerge`) — official docs say it works on Cloudflare Workers; automerge-repo sync servers exist (Express reference + community DO/PartyKit adapters — see below). CRDTs converge text but know nothing about *compilation* — they guarantee consistency, not correctness.

#### Yjs (YATA), Fugue/Loro — the performant list-CRDT family
- What it is: Yjs: production CRDT where *everything* (text, arrays, maps, XML) is squeezed into one list CRDT; items are (clientID, clock)-ID'd with left/right origins. Fugue (Weidner/Kleppmann): fixes the interleaving anomaly (concurrent inserts scrambling each other); Loro is a Rust CRDT lib implementing Fugue + Peritext-style rich text + moveable trees.
- URLs: https://github.com/yjs/yjs/blob/main/INTERNALS.md · https://www.bartoszsypytkowski.com/yata/ · https://arxiv.org/html/2305.00583v3 · https://loro.dev/blog/crdt-richtext · https://github.com/loro-dev/crdt-richtext
- Core mechanism: Position identity is decoupled from index: an insertion names its left (and right) neighbor *by ID*, so merges need no index transformation — and state vectors give diffs between replicas for incremental sync.
- Transferable mechanism: **Interleaving matters for code**: two agents inserting text at the same spot can produce semantically garbage merged text that *converges* but doesn't parse; Fugue's maximal-non-interleaving property is the formal criterion a code-merge CRDT needs — convergence alone is insufficient. Loro's moveable-tree CRDT (from "A Highly-Available Move Operation for Replicated Trees") is directly the primitive for tree-structured source.
- Status/limitations: Yjs is pure JS — trivially runs in Workers and has mature sync protocols (y-protocols, and Cloudflare ships y-partyserver). Loro ships WASM + JS. Both are viable in a 48h build.

#### Eg-walker — CRDT without per-character metadata
- What it is: EuroSys'25 paper (Gentle & Kleppmann): a text-collaboration algorithm that keeps an *event graph* and reconstructs document state by walking it — order-of-magnitude less memory than CRDTs, fast branch merges unlike OT.
- URLs: https://arxiv.org/pdf/2409.14252 · https://github.com/josephg/egwalker-paper/
- Core mechanism: Store the operation history (event graph with happens-before edges) as the source of truth; materialize any version by replaying ops in a deterministic topological order with a small CRDT only during the merge walk.
- Transferable mechanism: The *history is the database* — you never need to store the "merged state," only the op log; any view (a file, a review diff, a resolved repo) is a pure function of the event graph. For agents: the repo's source of truth can be the append-only op log; checkouts, diffs, and conflict surfaces are all recomputable views.
- Status/limitations: Reference TypeScript implementation + optimized Rust (diamond-types) exist; algorithm is self-contained enough for a custom build. Text-only in the paper — extending to trees is research, not product.

#### CRDTs/OT on source trees — CoAST, Denicek/mydenicek, Radicle COBs, Zed
- What it is: CoAST (scitepress 2022): an AST-based CRDT for collaborative program editing (shared program = syntax tree, ops carry logical timestamps). Denicek (Petříček & Edwards, UIST'25): programs = *edit histories* over structured documents; merging histories and conflict resolution are substrate primitives; mydenicek extends it with an event-DAG CRDT + path-selector OT. Radicle COBs: issues/patches stored as graphs of git objects — later *removed* dedicated CRDTs because "the union of Git DAGs is enough" (deterministic traversal of a merged commit DAG gives convergence for free). Zed: production editor where buffers are CRDTs over immutable inserted-fragment IDs (rope/SumTree) with Lamport clocks.
- URLs: https://www.scitepress.org/Papers/2022/112788/112788.pdf · https://tomasp.net/academic/papers/denicek/uist-2025.pdf · https://github.com/krsion/MyDenicek · https://radicle.dev/ · https://radicle.network/nodes/seed.radicle.dev/rad%3Az4V1sjrXqjvFdnCUbxPFqd5p4DtH5/commits/1dc799d679258663de2bd7d2dc31e9f708ab61f4 · http://zed.dev/blog/crdts
- Core mechanism (the synthesis): Model code collaboration at tree granularity (AST ops with IDs, or selector-path edits), or — Radicle's insight — let the *git DAG itself* be the convergent structure: merge two replicas' object graphs, deterministically traverse, done.
- Transferable mechanism: Edits addressed by *selector paths* (`/class/Foo/method/bar`, CSS-like — also used in gritzko's `be` AST VCS found in the same search) transform under concurrency the way OT transforms offsets; and git-object-union-as-CRDT means Artifacts' object store is already a convergence engine — no extra CRDT library needed for metadata-level collaboration.
- Status/limitations: CoAST/Denicek are research prototypes (papers + student implementations, not hardened libs); mydenicek is JSR-published TypeScript. Radicle is Rust/production. Zed is Rust — model only. All directly relevant prior art to cite in an idea card.

#### Git inside a Worker — isomorphic-git, wasm-git, gitoxide, web-tree-sitter, automerge-on-CF
- What it is: The deployment reality for a 48h Cloudflare build. isomorphic-git: pure-JS git (official Cloudflare Artifacts example + Workers guide). wasm-git: libgit2→Emscripten WASM (sync/async/OPFS variants). gitoxide: pure-Rust git; WASM support is a tracked *open* issue — many crates don't compile to wasm32 yet. web-tree-sitter: official WASM bindings with a documented `Language.loadSync(WebAssembly.Module)` path explicitly for Cloudflare Workers. Automerge: officially "works on Cloudflare Workers"; PartyKit's `y-partyserver`/`automerge-partyserver` give DO-backed CRDT sync; `automerge-cloudflare` (community) gives per-document DOs; Cloudflare's own `@cloudflare/computer` wraps isomorphic-git behind a SQLite VFS. `git-edge` (community): object-level three-way merge on top of isomorphic-git needing no worktree — designed exactly for edge/bare repos.
- URLs: https://isomorphic-git.org/docs/en/next/guide-cloudflare-workers · https://developers.cloudflare.com/artifacts/examples/isomorphic-git/ · https://isomorphic-git.org/docs/en/merge.html · https://isomorphic-git.org/docs/en/next/mergeDriver · https://github.com/petersalomonsen/wasm-git · https://github.com/Byron/gitoxide/issues/463 · https://www.npmjs.com/package/web-tree-sitter · https://automerge.org/docs/reference/library-initialization/ · https://github.com/nandan-varma/git-edge · https://github.com/just-be-dev/dockit/tree/main/packages/automerge-cloudflare · https://github.com/cloudflare/computer/blob/main/docs/13_git_interface.md
- Core mechanism: isomorphic-git's `merge` is a single-base diff3 — **no recursive merge bases, no strategy selection, and it needs a worktree**; but it exposes a `mergeDriver` callback (per-conflict-file custom algorithm) — a built-in plugin seam for a custom (e.g., structural) merger.
- Transferable mechanism: The real 48h architecture: Artifacts repos hold object graphs; a Worker does merges at **object level** (trees/blobs, à la merge-ort/git-edge) — never hydrate a worktree; plug structural merge in as a merge driver; use web-tree-sitter WASM for parsing in-isolate.
- Status/limitations: Verified: isomorphic-git + LightningFS MemoryBackend + ZenFS run in Workers; DO storage (SQLite: 2MB/pair, 10GB/DO) or R2 for blobs; no SSH transport, no partial-clone filters, no gc/worktrees. wasm-git exists but Worker-compat is UNVERIFIED (Emscripten + fetch assumptions). gitoxide: WASM target is a partial, tracked work-in-progress — don't plan on it.

## 8 mechanism seeds
1. **Conflicts as committable values**: store a merge's conflicted state as a first-class, rebaseable object (an odd-length tree list — `A+(C-B)` algebra that flattens by canceling terms), so integration never blocks and resolution is a separate later transaction (Jujutsu `merge.rs`).
2. **Shared normalized-conflict resolution cache**: hash conflicts after normalizing them (strip labels, drop ancestor, sort hunks) so a resolution computed once is replayed forever, repo-wide — resolution cost scales with distinct conflict *shapes*, not agents (git rerere).
3. **Selector-path edits on trees**: express agent edits as operations addressed by structural selectors (`/class/Foo/method/bar`) over an AST rather than byte ranges, then transform selectors under concurrency OT-style (Denicek/mydenicek; gritzko `be`).
4. **Speculation tree over conflicting changes**: partition pending agent commits into independent vs. conflicting sets by write-set intersection; land independents immediately and verify all orderings of the conflicting subgraph in parallel — out-of-order landing is safe iff every speculation path agrees (Uber SubmitQueue).
5. **The union of git DAGs is itself a CRDT**: drop dedicated CRDT machinery for repo metadata — merging two replicas' object graphs plus deterministic DAG traversal gives convergence for free (Radicle's post-CRDT COB design).
6. **Zero-copy overlay workspaces**: an agent's "worktree" is a named set of written files layered over an immutable server baseline — 100K workspaces cost ~files-touched each, and switching baseline is a pointer swap (Google CitC, Meta EdenFS).
7. **Anchored metadata that survives merges**: attach provenance/review/test annotations to stable inserted-element IDs inside the document rather than to line numbers, so context rides through every rebase and merge untouched (Peritext spans; Zed fragment IDs).
8. **Split merge into schema-merge and data-merge with different rules**: merge the repo's symbol/interface table under signature-level rules first (conflicts = API incompatibilities, detected early and cheaply), then merge bodies — mirroring Dolt's separate schema vs. cell-level merge.
