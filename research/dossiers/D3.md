## Part 1 — Multi-agent coding concurrency, 2025–2026

#### Git worktrees as the de-facto isolation primitive
- What it is: Multiple agents each get a separate working directory on its own branch, sharing one object store. This is the dominant pattern in 2025–2026 for local parallel agents.
- URL(s): https://code.claude.com/docs/en/worktrees, https://theroks.com/git-worktrees-and-ai-agents/, https://tim-schipper.nl/en/blog/git-worktrees-parallel-coding-agents, https://aidenapp.org/parallel-agents-git-worktree, https://www.neurals.ca/tech/claude/parallel-agents/
- Core mechanism: Isolation of the working copy (files, index, HEAD) while the object database stays shared — collisions become physically impossible, but coordination over *content* is entirely unsolved by the primitive itself.
- Transferable mechanism: Separate "what must not physically collide" (bytes on disk) from "what must not semantically collide" (interfaces, behavior). Worktrees prove the industry already accepts per-agent namespace isolation; the open problem is a shared registry of what each isolated workspace *means*.
- Status/limitations: Claude Code has first-class `--worktree` support incl. subagent `isolation: worktree` and `git worktree lock`. Caveats documented: new worktrees branch from remote default branch (`worktree.baseRef`), not local HEAD — uncommitted/unpushed context is silently absent. Isolation is filesystem-only; node_modules, ports, env aren't shared but also aren't coordinated.

#### Claude Code subagents, agent teams, orchestration shapes
- What it is: Anthropic's documented parallel patterns: worktree-isolated sessions, subagents with own context windows, experimental "agent teams" with shared task lists.
- URL(s): https://code.claude.com/docs/en/worktrees, https://blog.restatolabs.com/claude-code-git-parallel-workflows/, https://www.neurals.ca/tech/claude/parallel-agents/, https://weclaudecode.com/articles/parallel-worktrees
- Core mechanism: Three separable concerns — coordination (who owns a task), isolation (worktree), integration (a merge/verification lane). Restato Labs explicitly: "Git protects history, but it does not decide ownership or prove that combined changes work."
- Transferable mechanism: The split-work-by-contract pattern practitioners converge on: record per task (a) input commit, (b) owned files/subsystem, (c) interfaces it may consume but not modify — i.e., a declared read/write boundary per agent, essentially a crude transaction descriptor.
- Status/limitations: All file-level. No vendor ships semantic ownership or dependency validation.

#### Cursor Cloud Agents / Agents Window / subagents
- What it is: Cloud-hosted background agents (renamed from "Background Agents"), unlimited parallelism, env snapshots via `.cursor/environment.json`, an Agents Window, `/multitask` and "Build in Parallel" that runs independent plan steps concurrently.
- URL(s): https://cursor.com/docs/background-agent, https://cursor.com/help/ai-features/multi-agent, https://cursor.com/docs/subagents, https://forum.cursor.com/t/parallel-background-agents-with-shared-context/123718/3
- Core mechanism: Each agent = durable identity + own VM/environment + PR output; subagents get isolated context windows and return only results.
- Transferable mechanism: Environment-as-snapshot: the *dev environment itself* is a versioned, reproducible artifact decoupled from the code diff. Note Cursor docs frame it as coordinating "several" agents — nobody claims repo-level concurrency semantics.
- Status/limitations: Forum evidence confirms no built-in scheduling/dependency between agents; users hand-sequence ("shared feature first, then merge, then spawn"). API has `agent`/`run` split, 409 busy on concurrent run.

#### OpenAI Codex cloud tasks + subagents
- What it is: Cloud SWE agent; each task runs in its own isolated sandbox preloaded with the repo; tasks 1–30 min; also a documented subagent system (`/agent`, custom TOML agent definitions: `default`, `worker`, `explorer`).
- URL(s): https://openai.com/index/introducing-codex/, https://developers.openai.com/codex/subagents, https://help.openai.com/en/articles/20001545-using-codex-cloud
- Core mechanism: Task = isolated environment + commit + "verifiable evidence" (citations of terminal output/test logs) as the review surface.
- Transferable mechanism: Evidence-not-diff review: Codex's review unit is citations of what the agent *did and verified*, not the patch — aligns with "human decides, doesn't read."
- Status/limitations: Subagents spawn only on explicit request; orchestration is parent-agent-driven, token-expensive. No cross-task conflict handling documented.

#### GitHub Copilot cloud agent
- What it is: Assign an issue → Copilot works on a branch in a GitHub Actions-powered ephemeral dev environment → PR; iterate via `@copilot` comments, including "resolve merge conflicts."
- URL(s): https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent, https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task, https://github.blog/ai-and-ml/github-copilot/assigning-and-completing-issues-with-coding-agent-in-github-copilot/
- Core mechanism: Issue-as-prompt → Actions-runner sandbox → branch → PR; the GitHub issue/PR objects remain the coordination substrate.
- Transferable mechanism: Conflict resolution is delegated *back to the same agent* via comments — the retry-with-diagnosis loop is already productized, but the diagnosis is a raw git conflict, not a semantic one.
- Status/limitations: Sequential PR workflow; still assumes human review of diffs.

#### Google Jules + jules-sdk + jules-dispatch
- What it is: Async agent; pricing tiers literally sell concurrency (3/15/60 concurrent tasks); official SDK has `jules.all()` with `concurrency`/`stopOnError` options; third-party `jules-dispatch` orchestrates 10–50 sessions with an LLM planner and MCP server.
- URL(s): https://jules.google/, https://github.com/google-labs-code/jules-sdk/, https://www.npmjs.com/package/@google/jules, https://yuuqq.github.io/jules-dispatch/, https://developers.google.com/jules/api
- Core mechanism: Fleet fan-out: `Promise.all`-style batch API over sandboxed sessions, each producing a PR.
- Transferable mechanism: `--parallel N` runs the *same prompt* N times to produce N candidate implementations — "generate a population, then select" is already a shipping primitive (cheap clone-and-compete).
- Status/limitations: Coordination ends at the PR; nothing merges across sessions.

#### Devin (Cognition): managed Devins + Dynamic Workflows
- What it is: Coordinator Devin delegates to child sessions each in its own VM; "dynamic workflows" = a recorded, resumable Python script that fans out agents, pipes structured results between stages, and replays completed agents on resume.
- URL(s): https://cognitionai.mintlify.app/work-with-devin/advanced-capabilities, https://docs.devin.ai/work-with-devin/dynamic-workflows, https://cognition.com/blog/devin-annual-performance-review-2025, https://www.youtube.com/watch?v=ns1ifgYEGl0
- Core mechanism: The orchestration itself is code — deterministic, checkpointed, resumable — rather than an agent deciding live.
- Transferable mechanism: Recorded orchestration (replay-only-unfinished-work) is exactly a durable-execution primitive; maps directly onto Cloudflare Workflows/fibers. Also documented: fleet-per-repo migrations ("a fleet of Devins executes on every repo in parallel").
- Status/limitations: Docs explicitly warn against workflows "when the work is tightly coupled through shared state."

#### Cognition: "Don't Build Multi-Agents" → "Multi-Agents: What's Actually Working"
- What it is: Walden Yan's influential critique (parallel writers make incompatible *implicit decisions*) and the 2026 follow-up: multi-agent works where many agents contribute intelligence but writes stay single-threaded.
- URL(s): https://cognition.com/blog/multi-agents-working, https://news.ycombinator.com/item?id=45096962, https://agentic-ai.readthedocs.io/en/latest/ContextEngineering/devin/
- Core mechanism: Actions carry implicit decisions; parallel writers can't see each other's assumptions, so combined output is incoherent even when each part is locally fine.
- Transferable mechanism: The problem to solve is not merge-conflict-in-text but *decision collision* — a coordination system must externalize implicit decisions (read-sets, assumptions) so they can conflict-check before code exists. This is the strongest published argument for the brief's "transactional" thesis.
- Status/limitations: Cognition's adopted fix is "single writer, parallel readers" — they sidestep the problem rather than solve concurrent writes; a system that safely parallelizes writes would be genuinely differentiated.

#### Worktree/container-per-agent tools: Vibe Kanban, Conductor, Claude Squad, Crystal/Nimbalyst, Kungfu Kanban, Sculptor
- What it is: A category of schedulers: kanban board or tabs, each task gets a worktree (or Docker container), branch, terminal, diff view; human reviews and merges.
- URL(s): https://vibekanban.com/, https://github.com/bloopai/vibe-kanban/, https://superterminal.dev/blog/multi-agent-coding-tools-compared.html, https://kungfu-kanban.com/compare, https://agentpilotapp.com/shared/compare/vibe-kanban-alternatives/, https://imbue.com/product/sculptor/, https://imbue.com/blog/containers
- Core mechanism: Uniform recipe: worktree/container per agent + status board + human merge. Sculptor's differentiator is Docker isolation + Pairing Mode syncing container state into your IDE; Conductor's is task-claiming so two agents don't take the same card; Kungfu Kanban's is "runs-after" chains gated on the PR actually merging.
- Transferable mechanism: (a) Task claiming = crude exclusive ownership; (b) dependency chains gated on *merge events*, not task status — a state machine driven by integration outcomes; (c) Vibe Kanban's own framing: "the new bottleneck is planning and review" — the market already agrees humans are the constraint.
- Status/limitations: Notably: Vibe Kanban is sunsetting (per its README). All tools stop at "open a PR"; none touches semantic concurrency. This is the median solution the brief warns against — evidence it's already commoditized.

#### Factory Missions / Tembo multi-repo
- What it is: Factory decomposes projects into subtasks with "dependencies, ordering, resource allocation" across parallel Droids; Tembo runs agents per repo and emits *linked PRs* carrying cross-repo context.
- URL(s): https://factory.ai/product/missions, https://temboio.com/, https://www.tembo.io/blog/coding-agent-orchestration, https://www.tembo.io/blog/async-coding-agents
- Core mechanism: Linked changesets across repo boundaries — one logical change materialized as multiple PRs that reference a common parent task.
- Transferable mechanism: The "atomic multi-repo change" unit — a change is a graph of patches joined by an explicit parent identity, not a branch.
- Status/limitations: Tembo itself prescribes "explicit contracts" as best practice for cross-PR consistency — confirming contract-checking is done by humans today.

#### Graphite merge queue / stacked PRs
- What it is: Stack-aware merge queue with speculative execution: runs CI on multiple stacks in parallel ("parallel CI" uses speculative execution "similar to branch prediction"), batching, fast-forward merges; measured 1.5–2.5× faster merges.
- URL(s): https://graphite.com/docs/graphite-merge-queue, https://graphite.com/docs/merge-queue-optimizations, https://github.github.com/gh-stack/reference/merge-api/
- Core mechanism: Serialize on a queue but *speculatively validate* combinations in parallel; commit only the combination that verifies — optimistic-concurrency-flavored integration with a correctness gate.
- Transferable mechanism: A merge queue is a sequencer + speculative validators: order arrival, test candidate compositions concurrently, discard losers. Directly reusable: "integration as speculation" — test N orderings/compositions, keep what verifies.
- Status/limitations: Still textual diff + CI; validation is whole-repo CI, expensive per agent at 100K scale.

#### Jujutsu (jj): first-class conflicts
- What it is: Git-compatible VCS where a conflict is recorded *inside the commit* as an ordered list of trees (base + alternating sides), resolvable lazily; operations never fail on conflict; conflicts can be rebased, merged, backed out.
- URL(s): https://docs.jj-vcs.dev/latest/conflicts/, https://github.com/jj-vcs/jj/blob/main/docs/technical/conflicts.md, https://docs.jj-vcs.dev/latest/git-compatibility/
- Core mechanism: Conflict-as-data: a conflicted state is a first-class, versionable object, not a blocking error state.
- Transferable mechanism: "Divergence is a value, not an exception" — represent an incompatible merge as a persistent composable object (A + (C−B) algebra, cancellation on flatten), letting conflict resolution become a separate, deferrable, parallelizable job.
- Status/limitations: Rust CLI, not on Workers; but the *representation* (odd-length tree lists) is trivially encodable in a git object model — usable inside Artifacts.

#### Mergiraf / difftastic: structural merge & diff
- What it is: Tree-sitter-based syntax-aware merge driver (3-way merge over ASTs via GumTree matching + PCS triples); difftastic = structural diff, explicitly does not do merges.
- URL(s): https://mergiraf.org/, https://mergiraf.org/architecture.html, https://github.com/wilfred/difftastic
- Core mechanism: Match syntax nodes across three revisions (top-down isomorphism + bottom-up similarity), merge at node granularity, flag delete/modify and duplicate-signature conflicts.
- Transferable mechanism: AST-level diff gives you the *write-set at symbol granularity* almost free — the same machinery that detects "both sides added a function named X" yields the semantic conflict detector.
- Status/limitations: Rust + tree-sitter grammars; tree-sitter has WASM builds (feasible on Workers, needs verification). Mergiraf still operates per-file, can't see cross-file symbol effects.

#### Empirical papers on agent PR concurrency
- What it is: First measurements of concurrent agent PRs and their conflicts.
- URL(s): https://arxiv.org/html/2607.04697v2, https://arxiv.org/html/2604.03551, https://cbsoft.sbc.org.br/2026/data/papers/sbes/How%20AI%20Coding%20Agents%20Resolve%20Merge%20Conflicts%20An%20Empirical%20Study.pdf
- Core mechanism/findings: 40.2% of repos have co-active agent-authored PR pairs (79.4% of agent PRs are co-active); replayed 3-way merges: **cross-agent pairs conflict textually 41.7% vs 19.8% intra-agent**; ~42% of conflicts are *structural* (modify/delete, add/add). AgenticFlict: 27.67% conflict rate over 107K simulated merges. Third study: humans resolve 96.1% of agent conflicts; agent self-resolution varies ~60× by vendor.
- Transferable mechanism: Textual conflict rates are *lower bounds* on true incompatibility ("uncoordinated cost" per the paper) — empirical justification that the conflict surface must move off text. Also: agents almost never resolve their own conflicts today — an abort-with-diagnosis loop is unmet need, not established practice.
- Status/limitations: Datasets (AIDev, AIDev-pop) are public (Zenodo DOI 10.5281/zenodo.19396916) — usable to seed a demo.

#### CRDT / OT / Eg-walker collaborative editing
- What it is: Convergent concurrent-edit algorithms: Automerge merge rules per datatype; Peritext rich-text CRDT; Eg-walker merges long-diverged branches orders-of-magnitude faster than OT/CRDT predecessors.
- URL(s): https://automerge.org/docs/reference/under-the-hood/merge-rules/, https://www.inkandswitch.com/peritext/cscw-publication.pdf, https://dl.acm.org/doi/10.1145/3689031.3696076, https://xi-editor.io/docs/crdt-details.html
- Core mechanism: Make concurrent ops commutative/convergent by construction (stable element IDs, tombstones, append-only spans) so merging is deterministic and order-free.
- Transferable mechanism: For text/documents the industry solved "merge by construction"; code resists it because the unit isn't characters but *semantic referents* — suggests defining code changes on stable identity (symbol IDs/content hashes) instead of lines, which is where CRDT-ness could be imported.
- Status/limitations: Automerge is pure JS (runs on Workers). Applies to docs/state, not ASTs.

#### Multi-agent SE papers (SEW, AgentMesh, SEMAP, KGACG, Co-Saving)
- What it is: Workflow-generation (SEW, +12% LiveCodeBench), role-based teams (AgentMesh: Planner/Coder/Debugger/Reviewer), protocol-layer contracts (SEMAP on A2A: explicit behavioral contracts + structured messaging + lifecycle verification, up to 69.6% failure reduction), knowledge-guided (KGACG), token-saving (Co-Saving).
- URL(s): https://arxiv.org/pdf/2505.18646, https://www.arxiv.org/pdf/2507.19902, https://arxiv.org/html/2510.12120v1, https://www.arxiv.org/pdf/2510.19868, https://arxiv.org/pdf/2505.21898
- Core mechanism: SEMAP is the relevant one: formal *behavioral contracts between agents* measurably reduce coordination failures — evidence that explicit declared contracts beat implicit coordination.
- Status/limitations: All are benchmarks/papers, not products; coordination is still prompt-mediated, no storage-level mechanism.

#### Review-bottleneck evidence
- What it is: 2025 meta-analyses of real PRs.
- URL(s): https://tformance.com/report/, https://codepulsehq.com/research/code-review-study-2025, https://arxiv.org/html/2509.14745v2, https://arxiv.org/html/2509.19708
- Findings: 71% of GitHub PRs self-merge; 84–90% ship without formal review (90% for 1000+ line PRs); Code-AI correlates with +16–19% cycle time while Review-AI cuts review time ~54%; Claude Code PRs: ~84% merged, ~55% without modification. Reinforces the thesis: humans already don't read most code; the review surface must change, not be preserved.
- Status/limitations: Observational, not RCT (except METR, cited secondhand).

## Part 2 — Cloudflare itself

#### Artifacts
- What it is: "Versioned storage that speaks Git" — open beta since Oct 1, 2026; repos created/forked/imported programmatically; scales to "millions of repositories"; Git smart-HTTP remote + Workers binding + REST API. Launched private beta April 2026 alongside open-sourced **ArtifactFS** (mount large repos lazily, ~90–100s clone-time savings).
- URL(s): https://blog.cloudflare.com/artifacts-git-for-agents-beta/, https://blog.cloudflare.com/next-git-platform-on-cloudflare/, https://developers.cloudflare.com/artifacts/, https://developers.cloudflare.com/artifacts/api/git-protocol/, https://developers.cloudflare.com/changelog/post/2026-10-01-artifacts-open-beta/
- Core mechanism: Repo-as-primitive: repos are cheap enough to mint per agent/session/task; fork is a first-class API call.
- Transferable mechanism: "Fork per transaction attempt" is essentially free — the baseline snapshot for optimistic concurrency is `repo.fork()`. Git protocol support is v1/v2 clone/fetch/push; **no server-side merge exists — any merge/validation is the builder's code, which is the design space**.
- Status/limitations: Binding methods verified in brief; Workers Paid plan required; tokens are `art_v1_<hex>?expires=<unix>`.

#### Artifacts event subscriptions + Workers Builds
- What it is: Structured events consumable from a Worker: account-level (`repo.created/deleted/forked/imported`) and repo-level (`pushed`, `cloned`, `fetched`, `token.*`); an official guide wires `artifacts.repo.pushed` → Workflow → sandboxed CI → deploy; Workers Builds auto-deploys on push with Previews per branch.
- URL(s): https://developers.cloudflare.com/artifacts/guides/event-subscriptions/, https://developers.cloudflare.com/queues/event-subscriptions/events-schemas/, https://developers.cloudflare.com/artifacts/guides/build-and-deploy-on-push/, https://developers.cloudflare.com/changelog/post/2026-05-19-event-subscriptions/
- Core mechanism: The repo itself emits integration events — a commit is an observable signal in a durable event stream.
- Transferable mechanism: This is the stigmergic medium / message bus for free: "agent pushed" is an event any coordinator Worker can consume — no polling, no webhooks infra to build.
- Status/limitations: Events identify repo/branch/commit only; payload semantics are the builder's job.

#### isomorphic-git on Workers (official example)
- What it is: Pure-JS git running inside a Worker with an in-memory FS (`MemoryBackend`/ZenFS); official Artifacts example: create repo → commit → push, all in-Worker.
- URL(s): https://developers.cloudflare.com/artifacts/examples/isomorphic-git/, https://isomorphic-git.org/docs/en/next/guide-cloudflare-workers, https://github.com/isomorphic-git/isomorphic-git
- Transferable mechanism: A Worker can *programmatically construct and push trees* — i.e., a validator can synthesize the merged/committed state server-side without ever running a git binary or checking out a worktree.
- Status/limitations: Warning in docs: LightningFS may reorder writes → repo corruption risk without `flush()`; in-memory FS caps working set; no native merge driver — 3-way merge would be hand-built or via Sandbox.

#### Sandbox SDK (GA) + Sandbox 1.0 DO control
- What it is: Persistent container environments per name, `exec`, `gitClone`/`gitCheckout`, `writeFile`, PTY, preview URLs, snapshots (backup/restore), filesystem watching; GA April 2026; SDK 1.0 (Sept 30, 2026) lets *your own Durable Object class* own `ctx.container` — choose image/size per start, snapshot, control stop.
- URL(s): https://blog.cloudflare.com/sandbox-ga/, https://developers.cloudflare.com/changelog/post/2025-06-24-announcing-sandboxes/, https://developers.cloudflare.com/changelog/post/2025-08-05-sandbox-sdk-major-update/, https://developers.cloudflare.com/changelog/post/2026-09-30-sandbox-sdk-1-0/, https://developers.cloudflare.com/changelog/post/2026-04-13-containers-sandbox-ga/
- Transferable mechanism: Per-agent isolated execution where a *full git binary and test suite* can run — the "validation lane" (build the candidate composition, run tests) can be a sandbox fleet; snapshots = cheap transaction-checkpoint/rollback of an agent workspace.
- Status/limitations: `max_instances` configured per class; container startup is the latency floor for a demo — pre-warm for the wow scene.

#### Durable Objects (SQLite, gates) + Agents SDK + Project Think
- What it is: Single-threaded, globally-addressable objects with co-located SQLite; input/output gates serialize storage ops; ~500–1000 req/s per object; "scale out, not up." Agents SDK = `DurableObject > partyserver Server > Agent`, with WebSockets, scheduling, MCP. Project Think (`@cloudflare/think`, preview Apr 2026): fibers (checkpointable durable invocations), sub-agents with own SQLite + typed RPC, tree-structured forking sessions with FTS5, execution ladder (isolate→npm→browser→sandbox), self-authored tools.
- URL(s): https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/index.md, https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/, https://blog.cloudflare.com/sqlite-in-durable-objects/, https://developers.cloudflare.com/agents/runtime/lifecycle/agent-class/, https://blog.cloudflare.com/project-think/, https://github.com/cloudflare/agents/pull/1089
- Transferable mechanism: A DO is literally "a serializable transaction boundary you can name" — one DO per repo (or per symbol/region!) gives single-writer validation for free via input gates; Think's *tree-structured sessions* are exactly "agent context as a versioned, forkable artifact."
- Status/limitations: Single DO throughput is the 100K-scale constraint — a design must shard by region/symbol rather than bottleneck on one repo DO; Think is preview (APIs may change).

#### Workflows + v2 control-plane redesign
- What it is: Durable step execution (`step.do` memoized/retried, `waitForEvent`, sleeps), `AgentWorkflow` with RPC/progress to agents. Blog details a real re-architecture: V1 used a *single Durable Object as the account-wide registry/coordinator* which bottlenecked at agent-machine speed; V2 went horizontal.
- URL(s): https://developers.cloudflare.com/workflows/, https://developers.cloudflare.com/agents/concepts/workflows/, https://developers.cloudflare.com/workflows/get-started/durable-agents/, https://blog.cloudflare.com/workflows-v2/
- Transferable mechanism: Cloudflare's own war story is the scale argument: *a single coordinator DO per account didn't survive agent-speed fan-out* — directly relevant precedent for how to shard any "integration authority."
- Status/limitations: Docs explicitly recommend Workflows for durable orchestration + Agents for realtime — the demo combo.

#### Competition + public reaction
- What it is: Official page, blog, terms PDF (US/Canada only, permissive license required, Oct 1–14 2026 window, winners announced Oct 16), changelog. HN thread (item 49947051, ~189 comments) is predominantly skeptical: "$25k in credits to build the next GitHub," spec-work framing, and — importantly — *many comments question the premise of thousands of agents on one codebase*; real gains seen as 1–3 agents + human; fears of "slop" and unreviewable CI volume. Zeli/hndistilled summaries corroborate. On X: Cloudflare's own post; Cloudflare PM Brayden Wilmoth amplifying; Zeke Sikelianos joking "has anyone built the next GitHub yet?"; at least one entrant (wongstack.com) publicly entering.
- URL(s): https://www.cloudflare.com/git-competition/, https://blog.cloudflare.com/next-git-platform-on-cloudflare/, https://www.cloudflare.com/documents/build-next-gen-git-platform-competition-terms.pdf, https://news.ycombinator.com/item?id=49947483, https://hndistilled.com/story/49947051/, https://zeli.app/story/49947051, https://www.techtwitter.com/tweet/57a93ae6-4116-4c06-ab6c-aeb822f2e157, https://nitter.cf/zeke/status/2107245824082403805, https://nitter.cf/BraydenWilmoth/status/2105663342987903131
- Transferable insight: Judges likely share the HN skepticism — a winning demo must *visibly resolve* a concurrent-write incompatibility, not just fan out agents; also explicitly "not GitHub-with-agents" per the blog, so a non-PR primitive has tailwind.
- Status: No evidence yet of what competitors are building publicly (see "found nothing" below).

## Part 3 — Analogies (mechanism → structural mapping)

#### Stigmergy + Ant Colony Optimization
- What it is: Indirect coordination via environment: an action's trace in a shared medium stimulates later actions; ACO formalizes it — deposit pheromone ∝ solution quality, global evaporation, probabilistic path choice biased by τ.
- URL(s): https://en.wikipedia.org/wiki/Stigmergy, https://royalsocietypublishing.org/rsos/article/11/9/240845/92941/Stigmergy-from-mathematical-modelling-to, http://www.scholarpedia.org/article/Ant_colony_optimization, https://iridia.ulb.ac.be/~mdorigo/Published_papers/All_Dorigo_papers/DorDic1999cec.pdf, https://www.pnas.org/doi/10.1073/pnas.1509829113
- Core mechanism: Coordination without identity or messaging: shared mutable field + deposit rule + decay + attraction/repulsion response.
- Mapping: Agents deposit *intent markers* on symbols/files they're mutating (a "pheromone field" over the codebase); later agents read the field to steer around contested regions or reinforce proven paths; markers decay (TTL) so stale intent self-cleans. Quality-weighted deposit: verified/merged changes raise τ, aborted ones evaporate — the codebase accumulates a live "heat map of contention."
- Limitations: Needs a substrate (a DO-backed field over symbols); probabilistic steering, not guarantees.

#### Quorum sensing
- What it is: Bacteria constitutively emit autoinducers; when population density crosses a threshold, receptor binding flips population-wide gene expression (with autoinduction feed-forward).
- URL(s): https://pmc.ncbi.nlm.nih.gov/articles/PMC4313539/, https://pmc.ncbi.nlm.nih.gov/articles/PMC5056591/, https://www.nature.com/articles/nrmicro.2016.89
- Core mechanism: Cheap continuous signaling + a threshold that converts accumulated independent signals into a coordinated phase change.
- Mapping: A proposed interface change is dormant until *quorate*: it activates only when a threshold of dependent consumers (or verifiers) have signaled compatibly — replacing "merge when someone approves" with "activate when N independent signals accumulate." Signal weight can be typed (like species-specific AHLs): tests, consumers, reviewers are different autoinducers.
- Limitations: Metaphor for activation gating; the threshold rule must be designed to avoid gaming.

#### Clonal selection / germinal centers
- What it is: B cells somatically hypermutate, then compete in germinal centers for *limited* T-follicular-helper signals; higher-affinity clones get more help, divide more — and (2025 Nature) mutate *less* per division.
- URL(s): https://www.cell.com/immunity/fulltext/S1074-7613(16)30345-4, https://www.nature.com/articles/s41586-025-08728-2, https://doi.org/10.1146/annurev-immunol-120419-022408
- Core mechanism: Massively parallel variant generation + competition for a *scarce verification resource* + iterative rounds with fitness-proportional amplification and risk modulation.
- Mapping: Spawn N agent variants of a change; the scarce resource is CI/review budget ("Tfh help"), allocated to the currently-best variant by a measurable fitness (tests, contract conformance); winners get compute for refinement while losers die — and the better a variant is, the less it's perturbed. Jules' `--parallel N` shows the generation side already ships; selection-for-resource is the novel half.
- Limitations: Needs a cheap scalar fitness; wasteful by design (that IS the mechanism — parallelism is cheap, verification is not).

#### Gene regulatory networks / lac operon combinatorial promoters
- What it is: A promoter's *architecture* — arrangement of repressor/activator/RNAP sites — computes a function of transcription-factor concentrations (lac = an intricate multi-threshold input function; mutations turn it into purer AND/OR).
- URL(s): https://pubmed.ncbi.nlm.nih.gov/17376875/, http://www.sfu.ca/~eemberly/phys847/papers/lac_logic.pdf, https://pmc.ncbi.nlm.nih.gov/articles/PMC2132448/, https://sites.math.rutgers.edu/~mischaik/papers/comprehensive_lac.pdf
- Core mechanism: Local cis-regulatory wiring composes global behavior: each gene's "integration rule" is an explicit combinatorial function of signals, not a central controller.
- Mapping: Give each code region/module a declarative *integration promoter*: "admit change iff (typecheck ∧ consumer-compat) ∨ owner-override, inhibited by open-incident" — per-region admission logic as data, composing into repo-level behavior without central arbitration.
- Limitations: Designing per-region rules costs effort; best for a small set of critical regions (API surfaces).

#### TCAS / ACAS II
- What it is: Collision avoidance where two equipped aircraft *coordinate RAs via Mode S intent messages*: first declarer transmits its chosen vertical sense; second generates a complementary RA; simultaneous noncomplementary selection is broken by a deterministic rule (higher Mode S address reverses); reversals exist for deteriorating encounters.
- URL(s): https://www.eurocontrol.int/sites/default/files/2025-09/eurocontrol-safety-acas-guide-5-0.pdf, https://www.faa.gov/documentLibrary/media/Advisory_Circular/AC_90-120.pdf, https://archive.ll.mit.edu/mission/aviation/publications/publication-files/ms-papers/Zeitlin_2006_DASC_MS-25973_WW-18698.pdf
- Core mechanism: Pairwise *intent exchange* → complementary (never identical) maneuvers + a symmetry-breaking rule (higher ID yields) + bounded re-negotiation (sense reversal) + multi-threat composite advisories.
- Mapping: When two in-flight changes collide on a dependency, agents exchange declared intents; one takes "climb" (adapt to the other's new interface) and one "descend" (proceed unchanged); ties broken by a stable priority ID; if the geometry deteriorates mid-resolution, a bounded reversal reassigns roles. Deterministic, provably complementary deconfliction without a central controller.
- Limitations: Works pairwise; multi-threat composite is the hard extension — exactly the honest caveat for N-way conflicts.

#### ATC flow management: GDP slots / CTOP trajectory options
- What it is: When demand exceeds capacity, the system assigns arrival *slots* (EDCTs) via Ration-By-Schedule; CTOP lets each operator submit a *Trajectory Options Set* — ranked route+delay preferences — and the algorithm assigns the most-preferred feasible option.
- URL(s): https://www.faa.gov/air%5Ftraffic/publications/atpubs/foa%5Fhtml/chap18_section_12.html, https://www.faa.gov/air_traffic/publications/atpubs/FAC/1710.html, https://ntrs.nasa.gov/api/citations/20170011251/downloads/20170011251.pdf, https://tfmlearning.faa.gov/tfm-training/atfm-basics/files/pdf/L4-Appendix%20A_Ground%20Delay%20Program.pdf
- Core mechanism: Convert unbounded simultaneous demand into ordered, pre-committed slots; participants express ranked alternatives, system allocates greedily by schedule order.
- Mapping: Contended resources (an API symbol, a merge window) get *slots*: agents file a TOS — ranked integration options ("take new API", "wait one cycle", "take deprecated compat path") — and a ration-by-schedule allocator grants feasible slots. Turns conflict resolution into allocation with declared preferences; fairness = schedule order, not race to merge.
- Limitations: Requires defining "capacity" per region (e.g., one non-conflicting writer per symbol per epoch).

#### CCP clearing: novation → multilateral netting → mutualization
- What it is: A clearinghouse *novates* every trade: the bilateral contract is extinguished and replaced by two contracts with the CCP, enabling multilateral netting (one net position per member per security) and guaranteed settlement via loss mutualization.
- URL(s): https://www.chicagofed.org/-/media/publications/understanding-derivatives/understanding-derivatives-chapter-2-central-counterparty-clearing-pdf.pdf, https://www.dtcc.com/products-and-services/clearing-settlement-services/equities-clearing/cns, https://riskhub.org/frm-i/course-content/financial-markets-and-products/central-clearing/netting-in-bilateral-and-centralized-markets-323
- Core mechanism: Substitute one counterparty for all pairwise relationships; obligations then collapse arithmetically (netting), and the CCP absorbs residual default risk.
- Mapping: Agents never merge against *each other* — every change is novated to face "the register/trunk" alone; pairwise compatibility matrices disappear, and changes whose effects cancel or overlap *net out* (e.g., two agents' edits to the same symbol collapse into one admitted position). Failed changes are a "default" absorbed by the scheme, not a pairwise dispute.
- Limitations: Netting requires a commensurable unit of obligation (symbol-level deltas); the CCP is a single point — mitigated by sharding.

#### Limit order book / continuous double auction
- What it is: Shared book of resting bids/asks; incoming orders match greedily under *price-time priority* (better price first, FIFO within price); unmatched orders rest; deterministic replay from journaled commands.
- URL(s): https://mechanisms.microprediction.org/mechanisms/cda.html, https://arxiv.org/pdf/2210.05447, https://github.com/stoxxi/orderbook
- Core mechanism: Deterministic matching rule over an explicit priority order; the state IS the queue; three axioms (price-time priority, positive spread, conservation) provably pin down the unique outcome.
- Mapping: Changes are *orders* with a declared "price" (priority/urgency/deadline) matched against a book of pending integrations under a published deterministic rule — no negotiation, full auditability, replayable; a "marketable" urgent change consumes resting capacity like a market order.
- Limitations: Priority-as-price invites gaming; needs an honest priority currency (compute spent? human rank?).

#### Railway token block (single-line working)
- What it is: One physical token per single-line section; interlocked instruments at both ends guarantee at most one token released at a time; possession is the sole authority to occupy the block.
- URL(s): https://en.wikipedia.org/wiki/Token_(railway_signalling), https://irfca.org/docs/single-line-block-instr.html, http://www.irot.in/pdf/snt/S22%20BLOCK%20WORKING%20S.L%20TOKEN%20&%20D.L.%20BLOCK%20INSTRUMENTS.pdf, https://tern-systems.co.uk/resources/KEY%20TOKEN%20SIGNALLING%20FOR%20THE%2021ST%20CENTURY_FINAL.pdf
- Core mechanism: A unique, non-duplicable lease object tied to a fixed section, with handover semantics (return token → section provably clear) — a mutex with physical custody and an audit trail of possession.
- Mapping: Per-region exclusive *write tokens* checked out from a DO (the block instrument): the token itself is an inspectable object recording holder, section, and validity window; long-section vs short-section tokens map to coarse vs fine granularity. Dead-simple, provable mutual exclusion where pessimistic locking is acceptable.
- Limitations: Serializes per region — correct for hot spots, wrong as the global policy; complements rather than replaces OCC.

#### Torrens title registry
- What it is: "Title *by* registration, not registration *of* title": the state register is conclusive (indefeasible), mirrors all current interests, and the curtain principle removes any need to search the chain of historical instruments; backed by an assurance fund.
- URL(s): https://en.wikipedia.org/wiki/Torrens_title, https://lr.law.qut.edu.au/article/download/63/61/63-1-124-1-10-20120619.pdf, https://posh.austlii.edu.au/cgi-bin/viewdoc/au/journals/MonashULawRw/1994/12.pdf
- Core mechanism: Replace provenance-search with a guaranteed current-state register; every dealing that matters must be on the register or it doesn't exist.
- Mapping: A *symbol register* as the sole truth: the current signature/owner/encumbrances (open change attempts, deprecation notices) of every symbol live in one authoritative table — agents check the register instead of reconstructing truth by walking history/diffs. "Unregistered interests don't exist" = undeclared dependencies can't silently break you; the abort-diagnosis is the assurance fund.
- Limitations: Register must be complete or the guarantee is false; cost of populating it = the real build.

#### Kanban / pull systems
- What it is: A kanban is a *signal authorizing* production or withdrawal — downstream consumption is what permits upstream work; WIP is explicitly capped; production-kanban and withdrawal-kanban are separate signals.
- URL(s): https://artoflean.com/reference/kanban/, https://artoflean.com/topics/kanban-pull/, https://www.learnleansigma.com/guides/pull-system/, https://dspace.lib.cranfield.ac.uk/server/api/core/bitstreams/74187913-a5a5-4042-9b5d-ee940d4424ea/content
- Core mechanism: Invert the permission direction: work is released *only* by a downstream withdrawal signal, and bounded WIP caps in-flight work.
- Mapping: Producer agents can't emit an interface until a consumer agent "pulls" it — the consumer's declared need IS the authorization to write; WIP caps bound the number of unmerged in-flight changes per module, throttling contention before it forms.
- Limitations: Presumes identifiable consumers; works where the dependency direction is known.

#### Jidoka / andon / poka-yoke / takt
- What it is: Jidoka = stop immediately on detected abnormality (built-in quality, separate human judgment from machine motion); andon = the visible line-stop signal any operator can pull; poka-yoke = devices making the error impossible; takt = pace set by demand.
- URL(s): https://global.toyota/en/company/vision-and-philosophy/production-system/index.html, https://www.toyota-global.com/company/history%5Fof%5Ftoyota/75years/text/entering_the_automotive_business/chapter1/section4/item4.html, https://mag.toyota.co.uk/13-pillars-of-the-toyota-production-system/, https://artoflean.com/uploads/2019/01/Basic_TPS_Handbook.pdf
- Core mechanism: Distributed halt authority + make-errors-impossible design + universal visibility of the abnormal.
- Mapping: Any agent (or the validator) can "pull the andon" — halt all integrations touching a tainted symbol until triage; poka-yoke = shapes that cannot express the error (typed change descriptors that can't reference symbols outside their declared write-set); takt = the integration rhythm published so agents pace submissions to verified throughput.
- Limitations: Cultural mapping is loose, but "stop-the-line as a first-class event" and "invalid states unrepresentable" are concrete build patterns.

#### ISO shipping container
- What it is: TC104 deliberately made the container a *performance standard* ("operational exchangeability," no material spec); corner castings/twistlock made any box handleable by any crane/truck/ship; loading cost fell $5.83→15.8¢/ton by handling cargo only twice.
- URL(s): https://press.princeton.edu/books/ebook/9781400880751/the-box-pdf, https://d37djvu3ytnwxt.cloudfront.net/asset-v1:DelftX+NGIx+3T2015+type@asset+block/The_standarized_container.pdf, https://www.richmondfed.org/-/media/RichmondFedOrg/publications/research/econ_focus/2012/q2-3/pdf/economic_history.pdf
- Core mechanism: Standardize the *interface points* of the unit (corners), never its contents — heterogeneity inside, uniform handling outside.
- Mapping: Define a sealed *change container*: fixed external interface (declared read-set, write-set, evidence manifest, verification hooks) regardless of which agent/model produced it — so any validator, reviewer, or integrator handles all changes identically and contents are never re-opened in transit (no re-reading code).
- Limitations: The hard part is choosing the "corner castings" — the minimal sufficient manifest schema.

#### Stare decisis / precedent
- What it is: Later courts follow or *distinguish* (scope-limit by material facts) precedent; *overruling* is the costly exceptional act; the constraint object is the ratio decidendi.
- URL(s): http://wrlsi.ca/wp-content/uploads/2020/06/VOL-41-pages-5-31.pdf, https://www.cambridge.org/core/journals/legal-theory/article/distinguishing-and-reinterpreting-in-the-reason-model-of-precedent/3E3B7FEB057867DF09250987ABE7728D, https://www.nber.org/system/files/working_papers/w12913/w12913.pdf
- Core mechanism: Decisions accumulate as scoped rules; new cases are resolved by distinguishing (narrowing scope) rather than re-deciding — consistency without a central legislator.
- Mapping: Integration decisions become *precedents*: when an abort/compat ruling is issued ("symbol X changed signature; consumer contract Y is required"), it is stored scoped-to-facts; future agents resolve against the precedent store cheaply, and only novel cases reach the validator/human.
- Limitations: Requires a fact-schema to make "material facts" computable.

## 8 mechanism seeds
1. **Novated integration** (CCP, Chicago Fed/DTCC): every change faces a single authoritative "register" rather than other changes — pairwise conflict matrices vanish and overlapping deltas *net out* before admission.
2. **Intent-message complementary advisories** (TCAS Mode S coordination): colliding agents exchange declared intents and take provably complementary resolution roles, ties broken by a stable ID — distributed deconfliction with no central arbiter.
3. **Intent-pheromone field with evaporation** (ACO/stigmergy): agents deposit typed, TTL'd intent markers on symbols; the live heat map both steers agents away from contention and becomes the human's review surface ("where the swarm fought").
4. **Conflicts as first-class versionable objects** (Jujutsu): store divergence as data (base + alternating tree sides), letting resolution be deferred, parallelized, assigned, and even rebased — merging never blocks.
5. **TOS slot allocation over hot symbols** (CTOP/RBS): agents file ranked integration options for contended regions; ration-by-schedule assigns slots — converts races into fair, auditable allocation with declared fallbacks.
6. **Germinal-center competition for scarce verification** (clonal selection): N variants per task compete for the bounded resource that actually matters — CI/review budget — with fitness-proportional amplification and reduced perturbation of leaders.
7. **Symbol registry as guaranteed title** (Torrens): a conclusive per-symbol register of signature/owner/encumbrances replaces history-search; unregistered dependencies legally "don't exist," and the abort-diagnosis is the assurance fund.
8. **Speculative sequencing lane** (Graphite parallel CI + merge queue): an arrival-order sequencer plus N parallel validators testing candidate compositions; the first composition that verifies commits — optimistic concurrency with a deterministic commit order and zero pairwise negotiation.
