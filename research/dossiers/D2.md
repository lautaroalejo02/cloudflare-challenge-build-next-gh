# Evidence Dossier — Researcher C: Concurrency, build graphs, search, economics, verification

Scope covered: optimistic concurrency, deterministic DBs, dependency-graph build systems, evolutionary program search, ownership/capability partitioning, economic contention mechanisms, verification evidence, and deterministic replay — plus feasibility notes for Cloudflare Workers + Artifacts.

## Concurrency control

#### Optimistic Concurrency Control (Kung & Robinson 1981)
- What it is: Foundational TODS paper defining non-locking concurrency control where transactions execute freely, then validate read/write sets at commit and abort on conflict.
- URL(s): https://dl.acm.org/doi/10.1145/319566.319567 ; https://eecs.harvard.edu/~htk/publication/1981-tods-kung-robinson.pdf
- Core mechanism: Read-phase execution against a snapshot + serial validation phase; commit iff no committed transaction intersected the transaction's read/write sets, else rollback.
- Transferable mechanism: The validation is a pure set-intersection check over *what an agent actually touched*, which is exactly the information a coding agent emits for free (files read = its context). The abort path is where the payoff lives: validation failure can carry the precise intersecting write, i.e., "the symbol you assumed changed, here is the new form" — a structured retry signal, not a merge conflict.
- Status/limitations: Trivially implementable in a Durable Object (single-threaded, serialized validation is free). Requires an instrumented agent to capture true read-sets; un-instrumented agents degenerate to file-level granularity.

#### Serializable Snapshot Isolation (PostgreSQL SSI)
- What it is: Production implementation (PG 9.1+) of Cahill/Röhm/Fekete 2008: run snapshot isolation but monitor rw-antidependencies to detect "dangerous structures" that precede serialization anomalies.
- URL(s): https://github.com/postgres/postgres/blob/master/src/backend/storage/lmgr/README-SSI ; https://vldb.org/pvldb/vol5/p1850_danrkports_vldb2012.pdf ; https://wiki.postgresql.org/wiki/SSI
- Core mechanism: First-committer-wins plus tracking of SIREAD predicate locks that survive commit; a transaction is aborted only when it forms the pivot of a rw→rw→rw cycle, not on every read/write overlap.
- Transferable mechanism: Weaker and cheaper than full OCC validation: two agents may touch overlapping read-sets without aborting as long as no "dangerous structure" forms — directly reduces abort rate for symbol-granularity transactions where agents read-shared interfaces.
- Status/limitations: False-positive aborts exist by design; in PG the bookkeeping is nontrivial (predicate lock manager) but a simplified in-memory version over symbol versions is 48h-feasible inside a DO.

#### Calvin (deterministic distributed transactions)
- What it is: SIGMOD'12 system that reaches Paxos agreement on *transaction inputs* (a log), then executes deterministically — replicas replay the same serial order with zero commit coordination.
- URL(s): https://cs.yale.edu/homes/thomson/publications/calvin-sigmod12.pdf ; https://dl.acm.org/doi/10.1145/2213836.2213838
- Core mechanism: Agreement moves from "commit outcome" to "input order"; once a global order is fixed, every node computes identical results and no 2PC/locking across partitions is needed.
- Transferable mechanism: A single ordered log of agent-transactions (one DO or a Workflows queue is the sequencer) turns "merge" into a deterministic function of log position — every replica, preview, and test runner computes the same codebase state with no coordination.
- Status/limitations: Requires read/write sets declared or inferable upfront (Calvin aborts/restarts transactions that discover new dependencies mid-flight — a real constraint for exploratory agent work). DO sequencing is easy; deterministic *agent output* is not (LLMs nondeterministic), so determinism applies to integration, not generation.

#### Software Transactional Memory (Haskell STM)
- What it is: In-memory transactions with `retry` (block until a read TVar changes) and `orElse` (compose alternatives), giving composable atomic blocks.
- URL(s): https://www.microsoft.com/en-us/research/wp-content/uploads/2005/01/2005-ppopp-composable.pdf ; https://hackage.haskell.org/package/stm/docs/Control-Monad-STM.html
- Core mechanism: `retry` registers interest in the transaction's read-set and suspends until any read TVar changes — waking is driven by the read-set, not polling.
- Transferable mechanism: An agent's failed commit doesn't requeue blindly — it *subscribes* to its read-set symbols and is re-awakened exactly when the invalidating write lands, carrying the new value. Read-set doubles as a notification subscription.
- Status/limitations: Maps well onto DO alarms/WebSocket subscriptions + Artifacts push events. `orElse` (fallback branches) is less obviously useful for agents.

#### Escrow / commutative operations
- What it is: O'Neil 1986 escrow method: long transactions reserve quantities on hot fields via bounded increments/decrements; a logical field tracks inf/val/sup across in-flight transactions.
- URL(s): https://dl.acm.org/doi/10.1145/7239.7265 ; https://mwhittaker.github.io/papers/html/o1986escrow.html ; https://ics.uci.edu/~cs223/papers/p405-o_neil.pdf
- Core mechanism: Replace read-then-write on contended fields with commutative operations carrying an invariant predicate; operations from different transactions commute and only fail if the invariant can be violated under the worst-case abort/commit mix.
- Transferable mechanism: Defines a class of code changes that *never conflict*: appending to a registry/list, adding a test case, inserting a new function into a module are all commutative ops — the merge layer can certify commutativity (different symbols, same file) and integrate without validation round-trips.
- Status/limitations: Directly implementable: symbol-level AST ops are checkable with tree-sitter WASM. UNVERIFIED: no prior art found applying escrow semantics to code artifacts specifically (only DB numeric fields).

## Dependency-graph build systems

#### Bazel remote caching & Remote Execution API
- What it is: Builds decompose into actions with declared inputs/outputs; a remote cache maps action-hash→result metadata over a content-addressable store (CAS) of outputs.
- URL(s): https://bazel.build/remote/caching ; https://github.com/bazelbuild/remote-apis
- Core mechanism: hash(action inputs + command + env) → cached outputs; "never run the same action twice" is a pure function of content, not of who ran it or when.
- Transferable mechanism: A repo of agent changes can key *verification evidence* by content hash: hash(diff, baseline-commit, test-suite-id) → result. Two agents producing identical code get the same proof for free; review becomes "does a passing artifact exist for this content hash" rather than re-running tests.
- Status/limitations: A CAS is trivial over Artifacts (git objects are already content-addressed — the primitive gives blob/tree/commit hashing natively). Building a real action-graph is heavy; a demo can fake the action layer but the CAS/hash keying is real and cheap.

#### Nx "affected" computation
- What it is: CI feature computing the minimal project set touched by a PR: changed files → owning projects → transitive dependents; task-level variant (`NX_LEGACY_AFFECTED=false`) selects individual tasks by input globs.
- URL(s): https://nx.dev/docs/features/ci-features/affected ; https://nx.dev/docs/concepts/mental-model.md
- Core mechanism: Blast radius = files-changed → graph-reachable dependents; correctness evidence needed for a change is proportional to the affected set, not the repo.
- Transferable mechanism: For 100K agents, the *integration cost per transaction* is O(affected symbols/tests), not O(repo). The same reverse-dependency walk doubles as the abort-diagnosis: "your transaction conflicts because agent X's commit reached your read-set via these three edges."
- Status/limitations: Needs a symbol/import dependency graph per repo — buildable with tree-sitter for a demo subset of languages; plugin-specific "nature of change" analysis is the deep part (mock it).

#### Buck2 + DICE
- What it is: Meta's build system powered by DICE (Distributed Incremental Computation Engine): a demand-driven incremental computation graph with early-cutoff — if a dependency recomputes to the same value, dependents are not recomputed.
- URL(s): https://buck2.build/docs/insights_and_knowledge/modern_dice/ ; https://github.com/facebook/buck2/blob/main/dice/dice/docs/index.md
- Core mechanism: Nodes store versioned values + recorded dependency edges; invalidation propagates down from changed leaves but recomputation stops early wherever a node's inputs resolve to equal values.
- Transferable mechanism: Early-cutoff is the agent-scale insight: an agent's symbol change that produces an *identical interface* (refactor that preserves signatures) invalidates nothing downstream — transactions touching the same file commute automatically at the value-equality level.
- Status/limitations: DICE itself is Rust/embedded in Buck2 (not usable on Workers); the pattern (versioned memoized function graph) is reimplementable in TS inside a DO at demo scale. Salsa (Rust) is the analogous library — also not Worker-compatible; no pure-JS incremental engine verified.

#### Pants dependency inference
- What it is: Pants v2 infers file-level dependencies by parsing imports instead of hand-maintained BUILD metadata; ~30% finer dependency sets and up to 90% smaller BUILD files.
- URL(s): https://www.pantsbuild.org/blog/2020/10/29/dependency-inference ; https://www.pantsbuild.org/stable/docs/introduction/how-does-pants-work
- Core mechanism: The dependency graph is *derived from the code itself* (import statements → file-level edges), so it's always accurate and needs no curation.
- Transferable mechanism: Critical for agents: the read-set/conflict graph can be *recomputed from the code at each commit* rather than maintained — an agent's real dependencies are whatever it imports/calls, giving a self-maintaining coordination substrate with zero per-agent bookkeeping.
- Status/limitations: Directly feasible: tree-sitter WASM grammars parse imports for JS/TS/Python in a Worker. Whole-repo file-level graphs are bigger than one DO's memory at real scale — shard by package or keep graph in SQLite.

#### Nix derivations & content-addressing
- What it is: A derivation is a build spec over precisely-declared input store paths; outputs can be input-addressed (hash of spec+deps) or content-addressed (hash of output itself), with fixed-output derivations pinning a known hash to tolerate network access.
- URL(s): https://nix.dev/manual/nix/2.35/store/derivation/index.html ; https://nix.dev/manual/nix/2.34/store/derivation/outputs/content-address
- Core mechanism: Referring to outputs *before they exist* via deriving paths separates "what to build" (addressable spec) from "what was built" (verified content), and content-addressed outputs need no trust signatures.
- Transferable mechanism: An agent's change can be addressed as a *spec* (transaction description = task + baseline hash) whose output is verified by content-address — untrusted agent work becomes verifiable without trusting the agent, matching the "humans decide, don't read" thesis.
- Status/limitations: Conceptual transfer only; Nix doesn't run on Workers. Artifacts already gives git content-addressing — Nix adds the *spec-addressing* idea on top.

#### Turborepo task hashing / remote cache
- What it is: Cache key = hash(global inputs, package files, env, task config, dependent-task hashes); remote cache stores artifacts+logs keyed by that hash; optional HMAC signing of artifacts.
- URL(s): https://turborepo.dev/docs/core-concepts/remote-caching ; https://github.com/vercel/turbo/blob/main/crates/turborepo/ARCHITECTURE.md
- Core mechanism: Same fingerprint→outputs principle as Bazel but at package/task granularity with a plain HTTP cache protocol — the simplest proven version of evidence-by-hash.
- Status/limitations: Easiest of the build-graph mechanisms to crib for a 48h demo: hash→result JSON in a DO or Artifacts blob. Signature idea (HMAC over artifacts) is directly useful for untrusted agent evidence.

## Evolutionary / best-of-N program search

#### AlphaEvolve
- What it is: DeepMind's evolutionary coding agent: LLM ensemble proposes diffs to a working program; automated evaluators score; a program database (MAP-Elites + island models) selects parents for future prompts. Beat Strassen on 4×4 complex matmul (48 mults) and optimized Google infra.
- URL(s): https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/ ; https://arxiv.org/html/2506.13131v1
- Core mechanism: Evolution as *coordination protocol*: many candidates coexist, evaluators produce objective scalar scores, and the database resurfaces promising ancestors — improvement is a population process, not a single-thread edit loop.
- Transferable mechanism: Contention becomes a *population*: when N agents' transactions collide on a hot region, don't pick one — keep all N in an archive scored by machine-checkable evaluators, let tournament selection decide integration. Merge conflict → fitness competition with executable evidence.
- Status/limitations: Loop structure is simple (sample parent + inspirations → LLM diff → evaluate → add). On Workers: evaluator = Sandbox SDK or Workers AI; program DB = DO SQLite. Full AlphaEvolve needs ~100 compute-hours per eval — demo must use cheap evaluators (tests, typecheck, tiny benchmarks).

#### FunSearch
- What it is: Nature 2023, predecessor of AlphaEvolve: pairs pretrained LLM with a systematic evaluator to evolve *functions* (programs describing how to solve, not solutions); produced new cap-set bounds and bin-packing heuristics.
- URL(s): https://www.nature.com/articles/s41586-023-06924-6 ; https://deepmind.google/blog/funsearch-making-new-discoveries-in-mathematical-sciences-using-large-language-models/
- Core mechanism: An evaluator that mechanically scores each candidate guards against LLM hallucination; the LLM only supplies diversity — correctness pressure comes entirely from executable evaluation.
- Transferable mechanism: Separates the two roles cleanly: agents generate variation, *infrastructure* generates truth. In a multi-agent repo, the trusted component is the evaluator registry (tests, typechecks, contracts) — agents are interchangeable generators competing on it.
- Status/limitations: Simplest credible version of the evolutionary loop; needs only an eval function + pool. LLM calls via Workers AI binding (see pricing note) or external API.

#### MAP-Elites
- What it is: Quality-diversity algorithm keeping an archive of the best solution *per cell* of a user-defined feature space — returns a map of diverse high performers, not one winner.
- URL(s): https://arxiv.org/abs/1504.04909 (via https://ar5iv.labs.arxiv.org/html/1504.04909 ) ; https://members.loria.fr/jbmouret/qd.html
- Core mechanism: New candidates compete only against the elite occupying *their niche* (behavior-descriptor cell), so diversity is preserved structurally rather than by accident.
- Transferable mechanism: A review surface for 100K agents: instead of one winner per conflict, maintain a living map "best implementation per strategy-region" — the human sees the frontier (fast vs. safe vs. minimal-diff) as a map and picks a cell, not a diff.
- Status/limitations: Trivially implementable (dict keyed by descriptor cell + argmax); the hard part is choosing behavior descriptors for code changes — size, symbols touched, tests added, perf score are candidates.

#### Best-of-N with verifiers
- What it is: Inference-time scaling: sample N candidates, select via verifier — ranges from unit tests to learned reward models to symbolic equivalence partitioning (groups candidates by semantic behavior, picks from the dominant partition; HumanEval+ 0.728→0.803 at N=10) and probabilistic pivot tournaments (O(Nk) pairwise checks).
- URL(s): https://exa.ai/library/publication/8ml8hhmh4ft ; https://llm-as-a-verifier.com/docs/basic_usage/best_of_n_selection.html ; https://arxiv.org/html/2602.02143
- Core mechanism: Selection cost is O(Nk) pairwise comparisons or one partition pass — verification structure, not the generation, is the bottleneck and the lever.
- Transferable mechanism: Gives concrete machinery for "competing agents": symbolic-execution-free variant = run candidate diffs through the same test suite and partition by *failure signature* (which tests fail) — behavioral equivalence classes without SMT.
- Status/limitations: Test-based partitioning is cheap and real on Workers/Sandbox. LLM-as-verifier works via Workers AI but is probabilistic — prefer executable verifiers for the demo's integrity story.

## Ownership & capability partitioning

#### CODEOWNERS
- What it is: gitignore-style pattern→owner mapping; owners auto-requested on PRs touching owned files, can be required reviewers on protected branches.
- URL(s): https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners ; https://github.blog/news-insights/product-news/introducing-code-owners/
- Core mechanism: File-pattern authority claims enforced at integration time — ownership is routing metadata for human attention, not a lock.
- Transferable mechanism: For agents, "ownership" can be inverted: each symbol/region is owned by whichever agent's transaction most recently touched it — ownership = evidence responsibility; a new transaction on an owned region must carry proof it preserves the owner's invariants.
- Status/limitations: Trivial file; the interesting version is symbol-granular ownership, requiring the AST layer.

#### Bazel visibility
- What it is: Every target's `visibility` attribute lists which packages may depend on it; violations fail at analysis time, before build.
- URL(s): https://bazel.build/concepts/visibility
- Core mechanism: Dependency legality is a *declared, statically-checked property of the target* — the consumer cannot introduce an undeclared edge.
- Transferable mechanism: Agents can hold scoped write-capabilities declared per target/symbol-region; a transaction touching symbols outside its capability set fails at validation — partitioning enforced structurally, not by prompt instructions.
- Status/limitations: Trivial to enforce (set check at commit); the richer version needs the dependency graph (Pants-style inference) to detect *transitively* unauthorized reads.

#### Object-capability model (Miller et al.)
- What it is: Security model where an unforgeable reference both designates an object and grants the right to invoke it; "only connectivity begets connectivity" — authority propagates only through held references.
- URL(s): https://en.wikipedia.org/wiki/Object-capability_model ; http://www.erights.org/elib/capability/ode/ode-capabilities.html ; https://static.usenix.org/events/hotsec07/tech/full_papers/miller/miller_html/
- Core mechanism: Merge designation and permission into one token that can be delegated (with attenuation) but never forged or obtained ambiently.
- Transferable mechanism: An Artifacts write-token minted per-transaction IS an ocap (the primitive already mints read/write git tokens); extend the same pattern to symbol-region capabilities — an agent receives only the capabilities its task endowed it with, making over-reach structurally impossible.
- Status/limitations: Directly implementable: Artifacts `createToken` + per-path claims in the token payload checked by a DO. Attenuation/revocation supported natively (revokeToken exists).

#### Orleans virtual actors
- What it is: Grains (actors) have single-threaded, turn-based execution: one request runs to completion (or an await point) before the next starts; reentrancy is opt-in per call.
- URL(s): https://learn.microsoft.com/en-us/dotnet/orleans/grains/request-scheduling ; https://dotnet.github.io/orleans/docs/implementation/scheduler/
- Core mechanism: Serialize all mutations to an entity through a single activation — concurrency correctness emerges from the single-writer invariant, not from locks.
- Transferable mechanism: Durable Objects are already Orleans-style: one DO per repo (or per symbol-region shard) serializes all commit validation — a sharded "owner actor per region" gives linear scaling of coordination with region count, not agent count.
- Status/limitations: Native fit — DOs literally implement this model including input/output gates. Scaling beyond one DO per repo means sharding by region with cross-shard transactions becoming the hard part (Calvin-style ordering helps).

#### Rust ownership / borrow checker (analogy)
- What it is: Compile-time rule set: any number of shared borrows XOR exactly one exclusive borrow; violations are rejected before running.
- URL(s): https://doc.rust-lang.org/stable/book/ch04-02-references-and-borrowing.html ; https://google.github.io/comprehensive-rust/borrowing/borrowck.html
- Core mechanism: Exclusivity of mutation is checked statically by tracking who holds which kind of reference at each point — conflicts are type errors, not runtime races.
- Transferable mechanism: Treat a transaction's write-set as an `&mut` borrow of a symbol-region: the system statically refuses two live `&mut`s over the same region while allowing unlimited readers — enforcing Rust's aliasing discipline at the repo level turns scheduling into a borrow check.
- Status/limitations: Metaphor only; enforcement is still runtime validation in the DO (there is no compile phase). But the framing yields a clean rule set for demos.

## Economic mechanisms for contention

#### VCG / Vickrey auctions
- What it is: Truthful mechanism: winner pays the externality it imposes on others (second-price for single items); DSIC — truth-telling is dominant strategy.
- URL(s): https://en.wikipedia.org/wiki/Vickrey-Clarke-Groves_mechanism ; https://cs.brown.edu/courses/csci1440/lectures/fall-2025/vcg_mechanism.pdf ; https://milgrom.people.stanford.edu/wp-content/uploads/2005/12/Lovely-but-Lonely-Vickrey-Auction-072404a.pdf
- Core mechanism: Price = harm your allocation causes the losers' welfare; honesty is mechanically optimal.
- Transferable mechanism: Contended symbol-regions are allocated by second-price auction where bids are *declared priority/deadline budgets* — an agent that grabs a hot region pays (in scheduling delay or budget) what its presence costs the second-most urgent agent; self-rations contention without a queue master.
- Status/limitations: Winner-determination is trivial for single-region auctions, NP-hard for combinatorial bids — keep demo to per-region single-item auctions. No currency needed: bid in priority points earned by completed work.

#### Chubby & leases (Burrows 2006; Gray & Cheriton 1989)
- What it is: Chubby: coarse-grained lock service where a master holds a *lease* (majority promise not to elect another master for a term). Gray & Cheriton: time-bounded grants of cache-consistency authority — failures hurt performance, never correctness, and short leases bound the damage.
- URL(s): https://research.google.com/archive/chubby-osdi06.pdf ; https://dl.acm.org/doi/10.1145/74851.74870 ; https://web.stanford.edu/class/cs240/readings/leases.pdf
- Core mechanism: Ownership with a deadline: a lease grants exclusive authority for a term; expiry auto-reclaims, so crashes need no cleanup and contention resolves by waiting-at-most-lease-term.
- Transferable mechanism: Agents take short write-leases on hot symbol-regions instead of locks; lease expiry guarantees liveness when an agent stalls or dies, and lease *price* can float with demand (auction overlay above). Lease + OCC hybrid: lease only for regions whose contention rate exceeds a threshold.
- Status/limitations: DOs give strong per-object serialization already; leases matter for *cross*-DO/shard authority and for time-bounded exclusion in a demo. Clock skew is bounded inside one DO.

#### Congestion pricing / cloud spot markets
- What it is: Posted-price and auction mechanisms for perishable compute: dynamic prices by utilization, spot markets for spare capacity, hybrid on-demand/spot frameworks.
- URL(s): https://dl.acm.org/doi/10.1145/2843945 ; https://ar5iv.labs.arxiv.org/html/1201.5621 ; https://ar5iv.labs.arxiv.org/html/1704.05511
- Core mechanism: Demand exceeding capacity is signaled by price rather than queueing — agents self-select whether to pay now or defer/alternate-region.
- Transferable mechanism: A contended region's "merge priority" becomes a posted price that rises with the queue of pending transactions touching it; low-priority agents route around by choosing different regions (decompose work differently) — congestion signal = price gradient over the codebase map.
- Status/limitations: Needs a real scarcity to price — in the demo, price *integration-order* or *evaluator compute slots*, which are genuinely scarce; pricing code regions is metaphor-adjacent (fine for wow, flag it).

#### Internal prediction markets (Google, Ford)
- What it is: Companies ran markets on OKR achievement, deadlines, product quality; found ~25% MSE improvement over expert forecasts despite thinness and optimism bias; Google Cloud rebuilt one at scale (175K predictions, 10K employees).
- URL(s): https://www.columbia.edu/~bc2656/papers/CorporatePredictionMarkets.pdf ; https://cloud.google.com/blog/topics/solutions-how-tos/design-patterns-in-googles-prediction-market-on-google-cloud ; https://eudl.eu/doi/10.1007/978-3-642-03821-1_2
- Core mechanism: Consensus forecasts emerge from matching predictions-as-orders; informed participants profit by correcting the price — aggregation happens in the matching engine, not a meeting.
- Transferable mechanism: Agents (or their owners) trade on "will this transaction's candidate integrate by deadline / pass evaluation" — the market price is a live, decision-grade confidence signal that lets a human merge-or-reject without reading code; agents with private evidence profit by betting on themselves.
- Status/limitations: A minimal order-matching DO is buildable in 48h; market liquidity with few participants is the real-world caveat (Google's own paper documents thinness/optimism bias). Automated market maker (LMSR-style) avoids needing counterparties.

## Verification & evidence

#### Proof-Carrying Code (Necula & Lee 1996)
- What it is: Untrusted binaries ship with a formal proof of adherence to a consumer-published safety policy; the consumer runs a simple, fast, trusted validator — no crypto, no trusted third party.
- URL(s): https://www.usenix.org/conference/osdi-96/safe-kernel-extensions-without-run-time-checking ; https://people.eecs.berkeley.edu/~necula/pcc.html
- Core mechanism: Shift the trust burden: the *producer* must generate machine-checkable evidence; the consumer's validator is small enough to be trusted outright.
- Transferable mechanism: "Evidence-carrying commits": an agent's transaction integrates iff it carries a checkable artifact (passing-test trace hash, typecheck certificate, mutation-score delta) that a tiny validator verifies — review surface becomes "valid proofs attached" instead of diffs.
- Status/limitations: Real PCC proofs (verification conditions, TAL) are far beyond 48h — but the *shape* transfers: CAS-addressed evidence (test logs signed/stored in Artifacts) verified by a small Worker validator is very feasible and preserves the key property: verify the artifact, not the code.

#### CompCert verified compilation
- What it is: C compiler proved correct in Coq: generated assembly is semantically equivalent to source; ~90% of GCC -O1 performance; releases through 2024 (v3.15+).
- URL(s): https://compcert.org/ ; https://compcert.org/man/manual001.html
- Core mechanism: Semantic-preservation theorem: for all S compiled to C, observable behavior of C ⊆ behavior of S — miscompilation is impossible by construction.
- Transferable mechanism: Aspirational only — suggests "verified merge": an integration step that is *proved* semantics-preserving (e.g., commuting non-overlapping symbol edits is provably safe to reorder) rather than heuristically safe.
- Status/limitations: Not buildable; cite as the gold-standard limit case for "verify the transformation, not the output."

#### Property-based testing (fast-check)
- What it is: JS/TS QuickCheck: generates inputs against properties, shrinks counterexamples; test-runner agnostic (Jest/Vitest/Mocha/Bun/Node test runner).
- URL(s): https://fast-check.dev/ ; https://github.com/dubzzz/fast-check/
- Core mechanism: The spec is a universally-quantified predicate + input generators; the tool searches for counterexamples and minimizes them.
- Transferable mechanism: Gives agents executable contracts to optimize against without hand-writing test cases — the repo's invariants become *generator-driven*, so every candidate commit can be scored by the same property suite inside the evaluator.
- Status/limitations: Runs in Workers (pure JS, no native deps) and in Sandbox SDK. Strong demo asset: invariant definitions are short and readable.

#### Mutation testing (StrykerJS)
- What it is: Injects mutants into code, measures mutation score (killed/non-equivalent); Sentry reports real-world usage; StrykerJS supports incremental mode (reuse prior mutant results via diff) and per-test coverage mapping.
- URL(s): https://github.com/stryker-mutator/stryker-js/ ; https://blog.sentry.io/mutation-testing-js-sdks/ ; https://github.com/stryker-mutator/stryker-js/blob/master/docs/incremental.md
- Core mechanism: Test quality itself becomes a measurable artifact — a mutant surviving is an executable proof that the suite is blind to that change class.
- Transferable mechanism: Mutation score as *integration gate evidence*: an agent's commit carries not just "tests pass" but "tests detect perturbed behavior in the touched region" — distinguishes real verification from vacuous green builds at agent scale.
- Status/limitations: StrykerJS is Node-based; heavy for a 48h full run, but per-region incremental mode + a handful of mutants on touched functions is demo-feasible in Sandbox SDK.

#### Predictive test selection / test impact analysis
- What it is: Meta's system learns P(test fails | change) from history — 1/3 of tests, >99.9% of regressions caught; Google's ranking-based RTS catches 40% of failing commits at 0.9% cost via call-graph features; TestSage does function-level dependency selection for web services.
- URL(s): https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/ ; https://arxiv.org/html/1810.05286v2 ; https://research.google/pubs/regression-test-selection-at-scale-2/ ; https://lingming.cs.illinois.edu/publications/icst2019industry.pdf
- Core mechanism: Verification budget is allocated by learned failure likelihood per (change, test) pair — evidence-gathering is scheduled, not exhaustive.
- Transferable mechanism: At 100K agents you cannot run the affected set either — so the evaluator runs the *top-k highest-probability-of-failing tests per transaction*; a learned/empirical failure-rate per symbol-region substitutes for the model in a demo.
- Status/limitations: Static version (reverse-dep walk via inferred import graph) is feasible; ML version needs history — can mock the predictor while running real tests.

## Replayable / deterministic execution

#### rr record & replay
- What it is: User-space Linux record/replay: logs kernel inputs + CPU nondeterminism to a trace; replay under gdb is bit-exact every time; low overhead on low-parallelism workloads.
- URL(s): https://rr-project.org/ ; https://arxiv.org/pdf/1705.05937
- Core mechanism: Record the *nondeterministic inputs* to an execution, not the execution — replay re-runs with identical inputs so all state is reproduced.
- Transferable mechanism: An agent session is recordable the same way: log LLM responses, file reads, tool calls; replay produces the identical session — enabling audit, debugging of agent behavior, and counterfactual analysis ("replay this transaction against the new baseline").
- Status/limitations: rr itself doesn't apply (Workers is V8, no syscalls to record) but the *pattern* is pure software: agents already emit a tool-call trace; storing it in Artifacts as a first-class object is trivial.

#### Pernosco
- What it is: Omniscient debugger: builds a database of every program state from an rr trace; debugging becomes queries over the execution history; now open-sourced on-prem.
- URL(s): https://pernos.co/about/vision/ ; https://pernos.co/ ; https://github.com/Pernosco/on-prem
- Core mechanism: Debugging as data analysis — all states indexed, focus jumps anywhere instantly; "how did X happen" is a backward data-flow query.
- Transferable mechanism: Agent provenance queries: "which transaction/agent introduced this symbol version, and what evidence came with it" becomes a database query over the commit+evidence store — provenance is the review surface.
- Status/limitations: Heavy infra; the transferable part is schema design (index events by symbol, transaction, agent), which is just DO SQLite tables.

#### FoundationDB deterministic simulation
- What it is: Entire DB cluster runs inside one deterministic single-threaded simulator (Flow runtime does double duty); ~1 trillion CPU-hours equivalent simulated; every feature is tested under injected faults.
- URL(s): https://www.foundationdb.org/files/fdb-paper.pdf ; https://apple.github.io/foundationdb/testing.html
- Core mechanism: One runtime, two modes — production execution and deterministic simulated execution share the same code; faults/scheduling/network become controllable inputs.
- Transferable mechanism: A coordination layer written once can be *simulated* — the demo could show the same commit-validation logic running live and in a deterministic simulator where 10K synthetic agents stress it (the "100K agents" scale story becomes demonstrable, not asserted).
- Status/limitations: Building a deterministic simulator harness is real work but tractable for a small system (seeded RNG, virtual clock, async runtime shim). High-risk/high-reward for the wow-factor scale claim.

#### Antithesis
- What it is: Commercial deterministic simulation platform: custom hypervisor runs unmodified x86 systems on one core with perfect determinism, fault injection, intelligent (RL-guided) state exploration, property checks ("test without writing tests"), and perfect repro.
- URL(s): https://antithesis.com/ ; https://antithesis.com/docs/introduction/how_antithesis_works/ ; https://antithesis.com/docs/resources/deterministic_simulation_testing/
- Core mechanism: Determinism at the instruction level + a multiverse exploration loop — every event forks timelines; property violations are found by guided search, and any bug is exactly reproducible.
- Transferable mechanism: "Verification is the new bottleneck" is literally their pitch and matches the brief's thesis — the demo borrowable part is *property-based checks over a forked state space*: fork the repo N ways at a conflict point, evaluate all, keep the timeline where invariants hold.
- Status/limitations: Product, not buildable; note they market agent-facing skills/CLI — relevant prior-art signal that "agents need deterministic verification" is an emerging position.

#### Replay.io
- What it is: Runtime-replay browser (Chromium fork recording at library-call level) + Replay Protocol/ MCP letting coding agents analyze recordings: pause at points, evaluate expressions, inspect DOM/network at any time.
- URL(s): https://docs.replay.io/reference/time-travel/how-does-time-travel-work ; https://docs.replay.io/reference/replay-apis
- Core mechanism: Intercept nondeterministic OS/library calls and replay them — the recorder runs unmodified JS/WASM; inspection is an API over the recorded session.
- Transferable mechanism: Concrete prior art for *agent-facing record/replay*: their MCP server already lets an LLM agent time-travel a recorded app — for our domain, the equivalent is recording the repo's transaction history so agents can query "state at commit T" instead of re-running.
- Status/limitations: Their infra is browser-specific; the protocol design (session/pause/evaluate domains) is a good API template.

#### OT vs CRDT (collaborative editing)
- What it is: Two families for concurrent text merge: OT transforms operations against each other (usually serialized through a server); CRDTs make operations natively commutative. Eg-walker (EuroSys'25) claims order-of-magnitude improvements on both fronts.
- URL(s): https://xi-editor.io/docs/crdt-details.html ; https://dl.acm.org/doi/10.1145/3375186 ; https://dl.acm.org/doi/10.1145/3689031.3696076
- Core mechanism: Convergence by construction: either serialize-then-transform (OT, central authority) or design operations that commute regardless of order (CRDT, decentralized).
- Transferable mechanism: The dividing question for the whole challenge: *can agent code-changes be made commutative by construction* (symbol-level ops, unique-identity insertions) — if yes, no validation/ordering is needed at all for that class.
- Status/limitations: Text-level OT/CRDT merges characters, not semantics — code needs syntax awareness (see Mergiraf). Yjs/Automerge run in JS but merge text, not programs.

#### Saga / compensating transactions
- What it is: Long-running processes as local committed transactions + compensating transactions that semantically undo prior steps; pivot transaction = point of no return.
- URL(s): https://learn.microsoft.com/en-us/azure/architecture/patterns/saga ; https://en.wikipedia.org/wiki/Compensating_transaction
- Core mechanism: Isolation is traded for availability: intermediate states are visible, correctness is restored by explicit inverse operations after failure — "apology semantics."
- Transferable mechanism: "Merge first, verify, compensate": integrate agent work optimistically to keep velocity, run verification async, and on failure emit an *inverse commit* (a real, reviewable revert transaction) instead of blocking the pipeline — rollback becomes a first-class repo operation.
- Status/limitations: Inverse-commit generation is real work but bounded (git revert per transaction = fine for demo); the interesting version is a *semantic* compensation that preserves later committed dependents.

#### Mergiraf (syntax-aware merge)
- What it is: Tree-sitter-based structured merge driver: 3-way parses, GumTree matchings, PCS-triple merging; falls back to line merge; detects delete/modify and duplicate-signature conflicts. Prior art for AST-level merging.
- URL(s): https://mergiraf.org/ ; https://mergiraf.org/architecture.html ; https://codeberg.org/mergiraf/mergiraf
- Core mechanism: Merge operates on the syntax tree so non-overlapping structural edits (different functions, reorderings) merge cleanly where line diffs conflict.
- Transferable mechanism: The cheap first layer of a no-conflict pipeline: run symbol-aware merge; only transactions whose AST-level write-sets actually intersect escalate to semantic validation/OCC — most agent pairs commute for free.
- Status/limitations: Rust CLI — could compile to WASM for Workers (unverified whether a wasm build exists; grammars are already wasm). For the baseline's "no textual merge" thesis, Mergiraf is the competing answer and must be argued against (it resolves syntax, not semantics — two commits can merge cleanly and still be semantically incompatible).

## 8 mechanism seeds
1. **Leased contention with Vickrey pricing** (Gray & Cheriton + VCG): hot symbol-regions grant short write-leases auctioned second-price in priority credits — demand is priced and self-rationed, never queued by a master.
2. **Dangerous-structure aborts only** (PostgreSQL SSI/Cahill): allow overlapping read-sets freely; abort only the transaction forming an rw→rw→rw pivot, slashing abort rates vs. blanket OCC validation.
3. **Calvin-style input log** (Calvin): a single DO sequences all agent-transaction *inputs*; every replica, preview, and evaluator deterministically computes the same integrated codebase — merge is a pure function of log position.
4. **Commutativity certificates** (escrow/CRDT + Mergiraf): commits that only add new symbols or touch disjoint AST regions get a machine-checkable "commutes" certificate and integrate with zero validation round-trips.
5. **Evidence-carrying commits** (Proof-Carrying Code + Bazel CAS): a transaction integrates iff it carries a content-addressed artifact — test trace, typecheck result, mutation score — verified by a tiny trusted validator; reviewers check proofs, not diffs.
6. **Conflict tournaments** (AlphaEvolve/FunSearch + best-of-N partitioning): colliding transactions aren't serialized — their diffs enter a scored archive evaluated by executable tests partitioned by failure signature; selection is a tournament, not a merge.
7. **Compensating integration** (sagas): merge optimistically for velocity; async verification failures emit first-class *inverse commits* that semantically undo work while preserving later dependents — rollback as a reviewable repo operation.
8. **Deterministic multiverse evaluation** (FoundationDB/Antithesis): at each integration decision the system forks timelines under a seeded simulator, injects fault/load, and keeps the timeline where the property suite holds — the "does it work" question is answered by exploring branches, not by reading code.
